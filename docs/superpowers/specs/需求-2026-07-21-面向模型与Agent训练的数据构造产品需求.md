# 面向模型与 Agent 训练的数据构造产品需求

> 文档视角：模型训练与 Agent 训练的数据使用方 / 需求方  
> 日期：2026-07-21  
> 状态：需求建议稿

## 1. 核心判断

数据构造产品的价值，不是帮助用户“生成更多句子”，而是帮助用户把一个待提升的模型能力，稳定地转化为一份：

- 目标清楚；
- 覆盖完整；
- 标签可信；
- 边界明确；
- 可被训练；
- 可被评测；
- 可追溯和复用的数据资产。

对于模型训练，数据主要在教模型：面对什么输入，应该表现出什么行为。

对于 Agent 训练，数据还需要教 Agent：在什么状态下做什么决策、是否调用工具、调用哪个工具、传什么参数、如何利用工具结果，以及何时不应该行动。

因此，训练数据建设不是一个单纯的内容生成问题，而是一项“能力定义、数据规划、数据生产、质量控制、训练验证、问题回流”的闭环工作。

CorpusFlow 如果要更有效地帮助模型训练，应当成为这套闭环中的**数据设计与数据资产工作台**，而不只是数据生成器。

---

## 2. 用户是谁，他们真正要完成什么任务

### 2.1 主要用户

- 算法工程师：需要用数据修复模型能力、训练新能力，并判断新版本是否退化。
- Agent 工程师：需要训练或优化路由、工具选择、参数抽取、状态处理和最终回答。
- 数据产品经理 / 数据策划：需要把业务目标转成可执行的数据规划和验收口径。
- 评测 / 测试人员：需要建立独立、可信的评测集，并把 badcase 转成下一轮训练数据。
- 业务产品经理：需要确认模型学习的是正确业务规则，而不是数据中的偶然表达。

### 2.2 用户的核心任务

用户不是简单地“做一批数据”，而是要完成以下任务：

1. 定义这一轮训练到底要让模型学会什么、不能学错什么。
2. 判断需要哪些类型的数据以及各需要多少。
3. 生产符合目标的数据，并控制生成过程中的偏差。
4. 证明数据质量足以进入训练。
5. 确保训练集和评测集没有污染，评测结果可信。
6. 关联数据版本、训练版本和评测结果，判断改动是否有效。
7. 把新出现的失败重新转成下一轮数据，而不是每次从头开始。

## 3. 数据构造需求的两层结构

| 层级 | 定义 | 用户期望 |
| --- | --- | --- |
| 基本需求 | 决定一批数据能否被可信地用于训练 | 不出错、可复现、可验收、可追溯 |
| 期望型需求 | 决定数据工作能否高效、持续地提升模型 | 自动发现缺口、辅助规划、减少人力、形成闭环 |

基本需求没有满足时，生成越多，可能只是更大规模地放大错误。

期望型需求满足后，数据构造才会从一次性项目，升级为稳定的模型迭代能力。

## 4. 基本需求：训练数据首先必须做到什么

### 4.1 把训练目标变成明确的数据目标

每次数据任务都必须先回答：

- 要提升什么能力？
- 当前具体弱在哪里？
- 哪些行为应该被强化？
- 哪些相似行为必须被区分？
- 哪些行为绝对不能因为本轮训练而退化？
- 最终通过什么评测证明训练有效？

数据任务不应只记录“生成 800 条工具调用数据”，而应记录类似下面的目标：

> 提升试驾场景下天气工具的正确调用能力，同时保持普通天气咨询、非试驾咨询和其他工具路由不退化。

产品需要让训练目标、保护目标和验收指标成为数据任务的一部分，并贯穿生成、质检、导出和评测。

### 4.2 先设计数据结构，再决定生成数量

训练数据不能只按总条数管理，还应按模型真正需要学习的能力结构管理。

至少要支持：

- 能力类别：这一批数据分别训练哪些能力。
- 正样本：明确应该命中目标行为的样本。
- 难样本：表达接近、容易混淆，需要模型真正理解边界的样本。
- 负样本：明确不应该命中目标行为的样本。
- 关键交叉组合：两个或多个因素组合后是否都有覆盖。
- 保护集：用于防止已有能力退化的数据。

例如一个工具调用任务，不能只准备大量“提到天气就调用天气工具”的正样本，还要覆盖：

- 试驾计划 + 明确地点时间，需要调用天气工具；
- 只讨论试驾车型，不需要调用天气工具；
- 只闲聊天气但缺少必要信息，需要追问或普通回答；
- 与天气相似但应该调用其他工具的请求；
- 目标工具不可用、信息不足或用户撤销时的处理。

数据产品需要提供分桶、配额和覆盖检查，而不是只提供一个总生成数量。

### 4.3 建立可检查的数据契约

每份训练数据都应有明确的数据契约，即每个样本包含什么、每个标签代表什么、字段之间必须满足什么关系。

对普通模型训练，至少要明确：

- 模型看到了什么输入；
- 模型应该输出什么；
- 这条数据训练哪项能力；
- 这条数据属于正、难、负或保护样本；
- 理想答案中的事实和业务边界来自哪里。

对 Agent 训练，还应明确：

- 当前上下文和环境状态；
- 当前可用的动作或工具；
- 是否应该调用工具；
- 应调用哪个工具；
- 应提供哪些参数；
- 工具返回了什么；
- Agent 下一步应该如何处理；
- 最终任务是否成功。

产品应能检查字段完整性，也应能检查字段之间的逻辑一致性。例如：

- 标记为“不调用工具”的样本不能同时包含工具调用结果；
- 路由到普通问答的样本不能又标注必须调用业务工具；
- 工具名称正确但参数不完整，不能被判定为完全合格；
- 负样本不能因为答案写得通顺就被误当成正样本。

### 4.4 数据生产过程必须可控

无论数据来自人工编写、规则生成、模型生成还是线上日志，都应保留生产过程中的关键依据：

- 原始 seed 或原始 badcase；
- 生成目标与约束；
- 使用的生成策略；
- 使用的模型或数据来源；
- 哪些结果被过滤以及过滤原因；
- 哪些结果经过人工修改；
- 失败、超时或降级是否发生。

如果使用多个外部模型或多个账号并行生产，产品还应做到：

- 每条数据能够追溯到实际生产来源；
- 不允许在用户不知情的情况下自动切换为质量不同的备用来源；
- 生产失败的样本进入待处理队列，而不是静默丢失；
- 能比较不同来源的数据通过率、重复率和人工修改率。

### 4.5 质量检查不能只看格式

训练数据质检至少分为四层：

1. **结构质量**：字段完整、格式正确、能够被训练工具读取。
2. **语义质量**：输入自然、输出合理、没有答非所问或编造信息。
3. **标签质量**：能力类别、正难负属性、路由、工具和参数标注正确。
4. **集合质量**：总体比例合理、覆盖完整、没有明显偏科或偶然相关性。

产品既要支持自动质检，也要支持有重点的人工抽检。

人工不应平均检查每一行，而应优先检查：

- 系统低置信度的样本；
- 难样本和边界样本；
- 自动检查结果相互冲突的样本；
- 新能力首次进入训练的数据；
- 对训练结果影响较大的高权重样本；
- 不同生产来源中质量异常的一组样本。

### 4.6 必须控制重复、污染和切分泄漏

训练效果很容易被重复数据和评测污染制造出“虚假提升”。数据产品必须提供：

- 完全重复检查；
- 近似表达重复检查；
- 同一问题族、模板族或来源族检查；
- 新数据与历史训练集的重叠检查；
- 训练集与验证集、测试集的重叠检查；
- 同一问题的多个改写不得被随机拆到训练和验证两边；
- 独立评测集应冻结，不能在生成训练数据时被间接使用。

切分不能只按单条数据随机进行，而应按问题族、语义族、场景族或来源族整体切分。

产品需要输出清晰的污染与切分报告，使用户知道：

- 哪些样本被判定为重叠；
- 重叠发生在哪两个数据集之间；
- 哪些样本被剔除或重新分组；
- 最终训练、验证、测试各覆盖了哪些能力。

### 4.7 数据必须被当作有版本的数据资产

每次可进入训练的数据，都应形成不可混淆的正式版本，并能够回答：

- 这个版本由哪些原始数据和生成任务组成；
- 相比上一版本增加、删除、修改了什么；
- 使用了什么数据目标、规则和质量门槛；
- 由谁审核、何时通过；
- 用于训练了哪个模型版本；
- 后续发现问题时，能否定位到具体样本和来源。

数据版本应支持：

- 草稿、待审核、可训练、已使用、已废弃等状态；
- 版本间差异对比；
- 一键复现同一份训练数据；
- 保留修改前后的记录；
- 以稳定格式交付给不同训练工具。

### 4.8 数据必须能和训练、评测结果关联

数据产品不必亲自执行训练，但必须知道一份数据被用于什么训练，并接收训练后的评测结果。

至少应关联：

- 基础模型与起始版本；
- 本轮使用的数据版本；
- 训练方式和关键训练规模；
- 产出的候选模型或 checkpoint；
- 评测所用的模型精度和运行环境；
- 新能力指标、保护能力指标和失败样本；
- 最终是否允许进入下一环节。

模型选择不能只依赖整体 loss 或单一平均分，而应依据业务门槛：

- 目标能力是否提升；
- 保护能力是否退化；
- 结构和参数是否仍然稳定；
- 在真实部署精度和环境下是否成立；
- 是否出现新的系统性 badcase。

## 5. Agent 训练对数据构造的额外需求

### 5.1 Agent 数据不是普通问答数据

普通问答数据主要描述“输入—输出”。

Agent 数据描述的是一条决策链：

```text
用户目标
-> 当前上下文与环境
-> 是否需要行动
-> 路由到哪个能力
-> 是否调用工具
-> 选择哪个工具
-> 提取什么参数
-> 如何处理工具结果
-> 是否继续、追问、终止或回复
-> 任务最终是否成功
```

数据产品必须能够表达和检查这条链，而不能把所有错误都压缩成“最终答案不好”。

### 5.2 必须拆开训练和评测不同决策点

Agent 的以下能力应能分别构造数据、分别质检、分别评测：

- 意图与场景识别；
- 主路由选择；
- 是否需要工具；
- 工具选择；
- 参数抽取；
- 工具可用性判断；
- 工具结果理解；
- 多轮状态承接；
- 最终回复；
- 安全、权限和业务边界。

否则，一个样本即使最终结果失败，也无法判断应补哪一种数据。

### 5.3 必须管理决策之间的交叉关系

Agent 的数据风险往往来自偶然相关性。

例如，如果训练数据里所有天气问题都调用天气工具、所有普通问答都不调用工具，模型可能只学会“出现天气词就调用工具”，而没有学会真实业务条件。

因此，产品需要展示和检查类似下面的交叉覆盖：

- 场景 × 是否调用工具；
- 路由 × 工具；
- 工具 × 参数完整性；
- 用户表达方式 × 正难负类型；
- 工具可用性 × 应对策略；
- 单轮 / 多轮 × 决策结果；
- 目标能力 × 保护能力。

当某个组合只有单一结果或样本过少时，产品应提示潜在偏差，并建议补充反例或难例。

### 5.4 必须保留环境和工具条件

Agent 的正确行为取决于运行环境。同一句话在不同工具可用性、权限、时间、地点或会话状态下，正确动作可能不同。

Agent 数据因此需要保留：

- 当时可用的工具与能力；
- 工具的业务说明和约束版本；
- 用户已提供和未提供的信息；
- 会话状态与历史动作；
- 权限、地区、时间等环境条件；
- 工具执行成功、失败、超时或无结果的状态。

没有这些条件，模型容易学到互相矛盾的数据。

### 5.5 必须区分模型问题与确定性策略问题

不是所有 Agent badcase 都应该通过训练解决。

数据产品应帮助用户判断一个问题更适合：

- 补训练数据；
- 补评测数据；
- 修改提示或工具说明；
- 增加确定性 Policy 规则；
- 修复业务配置或接口；
- 进入人工复核。

CorpusFlow 不需要实现运行时 Policy，但应允许用户为 badcase 标记正确解决层，防止把所有系统问题错误地转成训练样本。

## 6. 期望型需求：数据产品还应该帮助用户做到什么

### 6.1 从训练目标自动生成数据规划

用户输入能力目标、已知 badcase、保护能力和预算后，产品能够建议：

- 需要哪些数据桶；
- 正、难、负样本的建议比例；
- 哪些关键交叉组合必须覆盖；
- 哪些历史数据可以复用；
- 哪些能力需要独立评测集；
- 哪些风险需要人工确认。

系统给出的是可编辑的数据规划，不应绕过用户自动决定业务边界。

### 6.2 自动发现覆盖缺口和错误相关性

产品能够从当前数据中发现：

- 某些能力没有难样本或负样本；
- 某些类别数量严重失衡；
- 某个工具只在单一场景中出现；
- 某条路由和某个工具被错误地绑定；
- 验证集缺少关键业务边界；
- 保护能力只有训练数据，没有独立评测数据；
- 大量数据只是同一模板的浅层改写。

用户看到的应是“缺什么、为什么有风险、建议补什么”，而不只是统计图。

### 6.3 从 badcase 和运行轨迹生成修复候选

产品能够接收：

- 模型评测失败；
- Agent trace；
- 工具调用日志；
- 用户反馈；
- 人工标注；
- 线上异常样本。

并将其转化为：

- 失败类型；
- 可能的修复层；
- 同问题族训练候选；
- 边界反例；
- 独立回归用例；
- 需要人工确认的问题。

每条新数据必须保留与原始失败证据的关联。

### 6.4 智能安排人工审核

产品应把有限的人审资源用在最有价值的地方：

- 优先展示高风险和低置信度样本；
- 对相似样本按问题族成组审核；
- 自动总结一组样本的共同修改原因；
- 根据审核结果调整后续生成和过滤策略；
- 允许抽样审核，并估算整批数据的风险；
- 明确哪些样本未经审核，不得冒充 gold 数据。

### 6.5 估算数据的训练价值，而不只统计数量

产品应逐步帮助用户判断：

- 哪些数据补的是新覆盖；
- 哪些数据只是重复已有能力；
- 哪些 badcase 在多个版本中反复出现；
- 哪些样本对区分易混淆行为最有价值；
- 哪些数据已被模型稳定学会，可以降低权重；
- 下一批预算更应该花在哪些数据桶。

数据数量不是核心成功指标，单位成本带来的有效能力提升才是。

### 6.6 支持训练版本间的数据归因

当新模型出现提升或退化时，用户希望追问：

- 哪批数据最可能带来了这项变化；
- 哪个能力桶在本轮明显增加或减少；
- 哪些标签、来源或生成策略对应异常 badcase；
- 是否因为验证集覆盖不足而选错了 checkpoint；
- 是否因为模型精度或运行环境不同而得出错误结论。

产品不需要声称自动证明因果，但应提供足够证据帮助用户定位。

### 6.7 沉淀可复用的数据资产和经验

用户应能复用：

- 经过验证的数据桶设计；
- 正难负样本模板；
- 业务边界和标签规范；
- 质量检查规则；
- 固定保护集和回归集；
- 常见 Agent 决策交叉矩阵；
- 历史 badcase 问题族；
- 已证明有效或无效的数据策略。

新任务应从已有资产开始，而不是每次重新写脚本、重新整理表格和重新解释业务规则。

## 7. CorpusFlow 最需要形成的七项产品能力

站在训练使用方视角，CorpusFlow 做到以下七件事，就能显著提高模型训练的数据质量和迭代效率。

### 能力一：训练目标与数据需求定义

把“要提升什么能力”转成可编辑、可验收的数据目标，明确目标能力、保护能力、边界行为和评测指标。

### 能力二：数据蓝图与覆盖规划

用能力桶、正难负比例和关键交叉组合规划数据，而不是只设置总生成条数。

### 能力三：可控的数据生产与审核

统一承接人工、模型、规则、日志和 badcase 来源，保留生产过程，支持重点质检和人工审核。

### 能力四：数据契约与质量治理

检查结构、语义、标签和集合质量，尤其能发现 Agent 路由、工具、参数和最终行为之间的矛盾。

### 能力五：数据版本、切分和防污染

管理正式数据版本，按问题族切分训练/验证/测试集，阻止重复、近重复和评测泄漏。

### 能力六：训练与评测结果关联

不必亲自训练模型，但能关联数据版本、训练产物、部署精度、评测环境和业务门槛，帮助选择真正可用的版本。

### 能力七：badcase 驱动的持续迭代

把评测失败和 Agent 运行轨迹重新转成问题族、数据候选、边界反例和回归用例，形成可持续的数据闭环。

---

## 8. 需求优先级

### 8.1 基本能力：缺失时不应声称数据可直接训练

- 训练目标和保护目标定义；
- 数据分桶、配额和覆盖检查；
- 模型与 Agent 数据契约；
- 结构、语义、标签和集合质检；
- 重复、污染和切分泄漏检查；
- 数据版本、来源和修改记录；
- 可复现导出；
- 数据版本与训练、评测结果关联。

### 8.2 期望型能力：帮助用户把训练做得更好、更快

- 自动生成数据规划建议；
- 自动发现覆盖缺口和偶然相关性；
- badcase / trace 到训练候选和回归用例；
- 风险导向的智能人审；
- 数据训练价值评估；
- 跨版本数据归因；
- 可复用的数据资产库和经验库。

## 9. 典型用户故事

1. 作为算法工程师，我希望先定义本轮目标能力和保护能力，以便数据生产不会只顾新增能力而造成已有能力退化。
2. 作为数据产品经理，我希望把数据拆成正、难、负和保护样本，以便模型学到真实边界而不是关键词相关性。
3. 作为 Agent 工程师，我希望查看场景、路由、工具和参数之间的交叉覆盖，以便发现训练数据中的错误绑定。
4. 作为算法工程师，我希望系统检查数据字段之间的逻辑冲突，以便错误标签不会进入训练。
5. 作为测试人员，我希望训练集和评测集按问题族隔离，以便评测提升不是由数据泄漏造成的。
6. 作为数据审核人员，我希望优先审核难例、低置信度和冲突样本，以便有限人力用于最高风险数据。
7. 作为模型负责人，我希望每个正式数据版本都能复现，以便训练出现问题时能够准确回退和定位。
8. 作为算法工程师，我希望数据版本能关联训练产物和评测报告，以便知道哪个版本为什么被选中或淘汰。
9. 作为 Agent 工程师，我希望工具调用数据分别评测是否调用、工具名称和参数，以便不被一个汇总准确率掩盖问题。
10. 作为业务产品经理，我希望把业务边界记录成可复用的数据规则，以便后续数据生产不再反复解释同一规则。
11. 作为评测人员，我希望将失败样本一键转成回归用例和训练候选，以便问题修复后不会再次出现。
12. 作为算法工程师，我希望系统发现验证集缺少的关键边界，以便 checkpoint 选择不再只依赖平均 loss。
13. 作为数据负责人，我希望比较不同生成来源的数据质量和成本，以便选择更稳定的数据生产方案。
14. 作为 Agent 工程师，我希望保留工具可用性和环境状态，以便同一句输入不会产生互相矛盾的训练标签。
15. 作为模型负责人，我希望区分训练问题、Policy 问题和业务配置问题，以便不把所有 badcase 都错误地交给微调解决。
16. 作为算法工程师，我希望新数据与历史资产自动查重，以便减少无效训练和重复成本。
17. 作为数据产品经理，我希望系统根据训练目标推荐数据蓝图，以便快速形成可讨论、可修改的数据方案。
18. 作为模型负责人，我希望在真实部署精度和环境下关联评测结果，以便实验室结论能够代表上线表现。

## 10. 验收标准

当 CorpusFlow 能满足以下场景时，可以认为它真正帮助了模型训练，而不只是帮助生成数据。

1. 用户可以从一个能力目标建立数据任务，并同时定义目标能力、保护能力和验收指标。
2. 用户可以按能力桶和正难负结构规划数量，并看到关键组合的覆盖缺口。
3. 系统能够检查普通模型样本和 Agent 决策样本的数据契约与逻辑一致性。
4. 每条生成数据都能追溯到原始 seed、badcase、生成来源、审核记录和正式数据版本。
5. 系统能够识别完全重复、近似重复和同问题族重叠，并按问题族完成训练、验证和测试切分。
6. 用户能够冻结独立评测集，并获知新训练数据是否与其发生污染。
7. 正式数据版本可以被原样复现，并能比较与上一版本的增删改差异。
8. 数据版本能够关联训练产物、评测环境和分项业务指标。
9. Agent 数据能够分别检查路由、是否调用工具、工具名称、参数、工具结果处理和最终回复。
10. 评测失败或线上 trace 能被转成带来源的问题族、训练候选、边界反例和回归用例。
11. 产品能够明确区分“适合补数据的问题”和“更适合 Policy、配置或工程修复的问题”。
12. 用户能够用同一套数据资产和验收口径比较模型版本，而不需要反复编写临时脚本和手工整理表格。

## 11. 成功指标

CorpusFlow 对训练工作的价值，应优先用以下指标衡量：

- 数据进入训练前的契约通过率；
- 难例、负例和关键交叉组合的覆盖率；
- 人工审核通过率与人工修改率；
- 训练集与评测集的污染率；
- 正式数据版本的可复现率；
- badcase 转为有效训练候选和回归用例的比例；
- 使用新数据后目标能力的提升幅度；
- 使用新数据后保护能力的退化幅度；
- 从发现问题到产出可训练数据的时间；
- 重复脚本、表格整理和人工对数工作的减少量。

不应把以下指标作为主要成功标准：

- 单次生成的总样本数；
- 支持多少种导出格式；
- 接入多少个外部模型；
- 页面上提供多少个配置项；
- 仅有整体 loss 下降但业务能力没有改善。

---

## 12. 产品边界

CorpusFlow 应负责：

- 训练目标到数据需求的转化；
- 数据规划、生产、审核和质量治理；
- 数据版本、血缘、切分和防污染；
- Agent 决策数据的结构化管理；
- 训练与评测结果的数据侧关联；
- badcase 到下一轮数据资产的回流。

CorpusFlow 不应负责：

- 实现具体模型训练框架；
- 管理 GPU、MLX 或盒子训练资源；
- 决定模型量化和部署方式；
- 取代完整评测执行平台；
- 实现 Agent 运行时 Policy；
- 自动代替业务方确认正确答案和安全边界；
- 在缺乏真实评测证据时承诺数据一定带来模型提升。

它应通过稳定的数据资产、训练记录和评测结果承接方式与这些系统协作。

---

## 13. 最终产品定义

从训练需求方视角，CorpusFlow 最合适的定义是：

> CorpusFlow 是面向模型与 Agent 迭代的数据设计和数据资产工作台。它把能力目标、业务边界和失败证据，转化为覆盖完整、质量可信、可训练、可评测、可追溯的数据版本，并帮助团队持续判断下一批最值得构造的数据是什么。

用户最终购买的不是“生成数据的效率”，而是三件事：

1. 更低的数据错误风险；
2. 更短的模型迭代周期；
3. 更有证据的训练决策。
