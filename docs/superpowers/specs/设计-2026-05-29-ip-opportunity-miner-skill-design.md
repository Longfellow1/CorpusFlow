# IP Opportunity Miner Skill 设计稿

日期：2026-05-29  
状态：设计草案  
目标形态：Codex skill / 本地研发项目知识产权机会挖掘流程

## 1. 背景

现有 AI 专利工具大多集中在“撰写”：根据技术交底书生成权利要求、说明书、摘要、OA 答复或专利检索报告。这个方向已经明显拥挤，且撰写本身不是最稀缺环节。

对研发团队而言，更前置、更难标准化的问题是：

- 当前项目里到底有哪些东西值得申请发明专利；
- 哪些内容更适合登记软著、写论文或作为商业秘密；
- 这些候选点是否有源码、测试、文档、实验数据作为证据；
- 在写交底书之前，发明人、研发负责人、IPR 应该确认哪些关键事实；
- 如何在不泄露未公开技术的前提下，引入 web 查新、竞品调研和文献检索。

因此，本 skill 的定位不是“AI 专利撰写器”，而是：

> 从代码仓库和研发材料中发现可讨论的知识产权机会，并把本地证据、外部证据和人工确认过程组织成可推进的决策材料。

## 2. 竞品观察

### 2.1 最接近的竞品：ALID

ALID 明确主打 invention discovery。其官网描述其读取 GitHub、Jira 和内部文档，发现可能可专利的 invention candidates，并提供 confidence score、source citations 和 draft Invention Disclosure Form。它还强调工程师从“主动提出发明”转为“审核 AI 结论”。  
来源：[ALID](https://www.alid.app/)

这说明“从工程资产反向挖专利点”是成立方向。但 ALID 主要面向 IP attorney / in-house counsel，重点仍在专利发现和 disclosure intake。

### 2.2 专利撰写与专利生命周期平台

Solve Intelligence 覆盖 invention disclosure、patent drafting、prosecution、claim charts 等专利流程。  
来源：[Solve Intelligence](https://www.solveintelligence.com/)

Patlytics 将 invention disclosure、drafting、invalidity、infringement detection、portfolio 等放入一个 AI patent platform。  
来源：[Patlytics](https://www.patlytics.ai/)

这类产品强在专利专业流程和企业 IP 工作台，但也意味着“AI 撰写专利”已经是红海。

### 2.3 Web 能力供应商

Tavily 提供 search、extract、crawl、map、research 等面向 AI agent 的 web 能力。  
来源：[Tavily Docs](https://docs.tavily.com/)、[Tavily Product](https://www.tavily.com/product)

Tavily 适合作为本 skill 的外部证据层，但不是产品壁垒。真正的壁垒是查询规划、脱敏策略、证据归因和人机确认流程。

## 3. 非目标

第一版不做以下事情：

- 不做“一键生成专利并宣称可授权”；
- 不替代专利代理人、IPR 或法务判断；
- 不默认上传完整源码、客户数据、内部项目名到外部服务；
- 不做完整专利管理平台；
- 不做完整论文自动写作；
- 不做“软著包过”或虚构源码、虚构说明书；
- 不把所有候选点都导向专利申请。

## 4. 核心差异化

### 4.1 Repo-first，而不是 disclosure-first

多数专利工具要求用户先知道自己要申请什么，再输入技术交底书。本 skill 反过来，从 repo、文档、commit、测试、fixtures、实验结果、issue 和设计记录中发现候选机会。

候选点不是从模型想象出来的，而必须绑定本地证据：

- 代码文件和符号；
- 测试用例或 fixture；
- 设计文档；
- 运行样例；
- 数据集或实验结果；
- 变更记录；
- 人工补充说明。

### 4.2 挖掘优先，撰写后置

本 skill 只负责把“值得讨论的点”挖出来、讲清楚、排优先级。撰写交底书、软著材料或论文大纲是后续分支能力。

推荐流程：

```text
项目扫描 -> 候选点挖掘 -> web 查新/竞品/论文检索 -> 人工确认 -> 分流到专利/软著/论文/商业秘密
```

### 4.3 人工确认是主流程

专利挖掘不能完全自动闭环。每个候选点必须经过人工确认，至少确认：

- 技术问题是否真实；
- 技术方案是否已经实现或计划实现；
- 关键区别点是否准确；
- 技术效果是否可证明；
- 是否已有公开披露；
- 哪些细节可以公开，哪些应保密；
- 推荐走专利、软著、论文还是商业秘密。

AI 的职责是降低人工判断成本，而不是绕过人工判断。

### 4.4 Web 是外部证据层

Web 调研分为四类：

- 专利查新：CNIPA、Google Patents、Lens、WIPO；
- 竞品查证：产品官网、文档、博客、开源仓库；
- 论文检索：Google Scholar、Semantic Scholar、arXiv、ACM、IEEE；
- 软著规则：官方版权登记指南、地方政务服务页、中国版权保护中心口径。

Tavily 可用于 search、extract、crawl、map、research；Exa 或普通 web search 可作为补充。所有外部查询必须先经过脱敏改写。

### 4.5 多出口分流

候选点不应全部导向发明专利。

| 候选点特征 | 推荐路径 |
| --- | --- |
| 技术问题明确、技术手段闭环、技术效果可验证 | 发明专利 |
| 软件系统完整、功能模块清楚、源码和文档可对应 | 软著 |
| 有数据集、实验设计、对比结果或方法论总结 | 论文 |
| 公开后容易被绕开、难以检测侵权、含业务规则或内部 know-how | 商业秘密 |
| 只是普通配置、页面、CRUD、流程编排 | 暂不推进 |

## 5. 目标用户

### 5.1 研发负责人

需要从项目中快速找出可申报成果，形成与 IPR 讨论的材料。

### 5.2 发明人/技术负责人

需要确认技术问题、关键步骤、实现事实、可公开范围和技术效果。

### 5.3 IPR/专利工程师

需要判断候选点是否值得进入检索、交底书、代理人撰写或内部提案流程。

### 5.4 论文/创新管理负责人

需要判断项目里是否有可形成论文、竞赛材料、技术白皮书或内部成果沉淀的内容。

## 6. 第一版 MVP

MVP 只交付一个核心产物：

```text
项目知识产权机会评估报告.md
```

报告包含：

- 项目资产概览；
- Top 10 候选机会；
- 每个候选点的推荐路径；
- 本地证据引用；
- web 相似方案；
- 初步差异化判断；
- 需要发明人确认的问题；
- 风险提示；
- 下一步材料清单。

MVP 不要求自动生成完整交底书，但可以调用现有 `patent-disclosure-skill` 作为后续动作。

> 报告强制免责声明（置于报告顶部）：本报告中的"web 相似方案""差异化判断"仅为讨论素材，**不构成查新报告、新颖性/创造性意见或可专利性结论**。web 未命中类似方案 ≠ 具备新颖性（专利文献并不都被 web 索引，正式查新需 CNIPA/Google Patents/专利数据库）。最终判断以专利代理人/IPR 为准。

## 7. 工作流设计

### 7.1 Step 1：项目资产扫描

输入：

- repo 根目录；
- 可选：项目说明、目标领域、企业系统模板、已有专利/软著/论文材料；
- 可选：用户指定重点模块；
- 已有 IP 材料目录（如 `docs/.../patents/`）：用于对已申报/已交底的点去重，避免把已经走过流程的候选重新刷出来。

资产扫描优先复用已有索引：如仓库存在 codegraph 索引（`.codegraph/`），资产地图、技术模块列表、调用链路应直接消费 codegraph 的符号/调用边/impact，而不是另写一套 AST 扫描。`repo_inventory.py` 退化为"读 codegraph + 补充文档/数据资产"的薄封装。

扫描对象：

- 源码目录；
- README、docs、specs、ADR；
- tests、fixtures、benchmarks；
- scripts、pipelines、数据处理工具；
- package 配置和依赖；
- issue/commit/PR 信息，如果可用；
- demo、截图、导出样例。

输出：

- 项目资产地图；
- 技术模块列表；
- 数据资产列表；
- 可疑创新信号列表。

### 7.2 Step 2：候选机会挖掘

从项目资产中抽取以下信号：

- 非普通业务逻辑的算法链路；
- 数据清洗、标注、转化、增强、评测流程；
- badcase、failure、eval、benchmark、regression 相关逻辑；
- 多模型、多 agent、多工具协同机制；
- 工程约束下的自动化决策；
- 可复现的数据集或实验流程；
- 解决“以前靠人工做”的流程；
- 项目中多处复用的抽象或协议（可用 codegraph callers/impact 判定复用广度）；
- 具有用户可感知效果的系统能力。

> 注意：信号清单只是"哪里去找"，不是判别标准。「值得讨论的技术点」与「普通 CRUD/配置/页面」的区分是本 skill 的核心难点，必须落到可判定的 rubric（见 §11），并先用真实 repo 跑出一版基线，而不是只靠模型直觉。

每个候选点生成一张 `Opportunity Card`。

### 7.3 Step 3：外部调研与查重

对每个高优先级候选点生成脱敏查询。

查询类型：

- 技术问题查询；
- 技术手段查询；
- 同类产品查询；
- 专利关键词查询；
- 论文关键词查询；
- 反向否定查询：寻找是否已有系统完整实现同一链路。

工具优先级：

1. 官方或权威来源；
2. 专利数据库；
3. 学术数据库；
4. 竞品官网和产品文档；
5. 搜索 API，例如 Tavily；
6. 普通 web search 兜底。

输出：

- 相似方案列表；
- 可能影响新颖性/创造性的公开材料；
- 可用于差异化论述的证据；
- 需要人工进一步确认的问题。

### 7.4 Step 4：人工确认

人工确认以表单或 checklist 方式进行。

每个候选点必须有以下状态之一：

- `推进专利`；
- `推进软著`；
- `推进论文`；
- `保密沉淀`；
- `合并到其他点`；
- `暂不推进`；
- `证据不足，补充材料后再评估`。

人工确认字段：

- 技术问题是否准确；
- 方案步骤是否真实；
- 是否已有公开披露；
- 是否已有同主题材料；
- 是否涉及客户/供应商/外部合作；
- 是否可公开关键实现；
- 推荐第一发明人/参与人；
- 需要补充的代码、截图、测试或数据。

### 7.5 Step 5：分支交付

确认后进入不同分支：

- 专利：调用或衔接 `patent-disclosure-skill`，生成交底书、技术附图、权利要求骨架、企业系统填报清单；
- 软著：生成软件名称建议、功能说明、设计说明书、用户手册、源码页抽取清单；
- 论文：生成论文选题、related work 查询矩阵、实验设计草案、可复现材料清单；
- 商业秘密：生成保密边界、不可公开点、内部留存证据清单。

## 8. Opportunity Card 数据结构

```yaml
id: IP-001
title: 候选点名称
route: patent | software_copyright | paper | trade_secret | hold
priority_score: 0.0-1.0   # 仅用于排序，不代表授权概率/可专利性判断
priority: P0 | P1 | P2 | P3
technical_problem: 解决的技术问题
technical_solution: 核心技术方案
technical_effect: 可验证技术效果
local_evidence:
  - path: 本地文件路径
    lines: 相关行号或章节
    reason: 为什么支持该候选点
external_evidence:
  - title: 外部材料标题
    url: URL
    relation: similar | different | risk | background
novelty_hypothesis: 初步差异化假设
human_questions:
  - 需要发明人确认的问题
risks:
  - 风险点
recommended_next_step: 下一步动作
review_status: pending | approved | rejected | merged | needs_evidence
reviewer_notes: 人工确认记录
```

## 9. Skill 形态设计

建议拆成一个总入口 skill 和三个分支 skill。

```text
ip-opportunity-miner/
  SKILL.md
  references/
    competitor_landscape.md
    evidence_model.md
    patent_route.md
    software_copyright_route.md
    paper_route.md
    web_research_policy.md
    human_review_checklist.md
  scripts/
    repo_inventory.py
    opportunity_table.py
    source_evidence_index.py
    softcopyright_source_export.py
```

### 9.1 `ip-opportunity-miner`

总入口。负责项目扫描、候选点挖掘、web 调研、人工确认表和总报告。

### 9.2 `patent-opportunity-route`

专利分支。复用已有 `patent-disclosure-skill`，但入口从“已确认候选点”开始，而不是从全项目重扫开始。

### 9.3 `software-copyright-route`

软著分支。负责生成真实项目材料，不虚构代码，不伪造功能。

### 9.4 `paper-opportunity-route`

论文分支。负责判断是否有研究问题、实验设计、可复现材料和 related work 空间。

## 10. Web/Tavily 使用策略

### 10.1 何时用

- 用户明确要求联网调研；
- 候选点进入 P0/P1；
- 需要判断相似竞品；
- 需要生成专利/论文关键词；
- 需要核对官方材料要求；
- 当前知识可能过期。

### 10.2 如何脱敏

禁止直接发送：

- 完整源码；
- 客户名；
- 内部项目名；
- 未公开产品名；
- 真实数据；
- 账号、密钥、URL、日志；
- 供应商或合作方敏感信息。

允许发送：

- 抽象后的技术问题；
- 通用技术术语；
- 不含业务主体的流程描述；
- 已公开的产品名或论文名；
- 用户明确同意公开的内容。

脱敏不能只靠模型自动改写后直接发送——LLM 改写仍可能漏出内部项目名/未公开产品名。早期版本采用**人工审核后的查询清单**机制：skill 生成候选脱敏查询 → 落盘 `web调研记录.md` 待发送区 → 用户确认后才真正发出。自动直发推迟到脱敏策略经过验证之后。

### 10.3 Tavily 的角色

Tavily 用作 agent web grounding：

- Search：快速获得候选来源；
- Extract：抽取指定网页正文；
- Crawl/Map：分析竞品官网或文档站结构；
- Research：对复杂主题生成初步调研底稿。

Tavily 结果必须二次过滤，不直接作为结论。高风险结论需要官方来源、专利数据库或论文数据库交叉确认。

## 11. 评分模型

候选点评分建议分为四类：

| 维度 | 说明 | 可判定锚点（0/0.5/1） |
| --- | --- | --- |
| 技术性 | 是否是技术问题和技术手段，而非纯业务规则 | 0=纯业务规则/配置/CRUD；0.5=有算法但等价于公开常规做法；1=对计算机内部数据处理有具体技术手段 |
| 证据强度 | 是否有源码、测试、数据、文档支撑 | 0=仅描述无代码；0.5=有源码无测试/数据；1=源码+测试/fixture/实验结果齐全 |
| 差异化 | 是否与公开方案存在可说明区别 | 0=已有系统完整实现同链路；0.5=有区别但难表述；1=有明确可论述区别点 |
| 可推进性 | 是否适合公开、是否能补齐发明人和材料 | 0=强烈建议保密/无法补齐；0.5=需较多补充；1=可公开且材料基本就绪 |

示例评分：

```text
总分 = 技术性 30% + 证据强度 25% + 差异化 30% + 可推进性 15%
```

评分只用于排序，不代表授权概率。各维度必须按上述锚点给分并在 Card 里写明依据，禁止只给一个无解释的数字。

## 13. 验收标准

用一个真实 repo 验收（推荐用 CorpusFlow 自身：它已手工挖过一次"失败证据"专利点，可作标准答案）：

- 至少产出 5 个候选机会；
- **精确率**：Top 10 候选里，人工判定"确实值得讨论"的占比 ≥ 60%（防止 skill 为凑数量刷低质候选）；
- **召回校验**：能否独立重新发现已手工识别的强点（如 CorpusFlow 的失败证据生成方法 + 6 种批次变体），且未把已申报的点重复刷出；
- 每个 P0/P1 候选点至少有 2 条本地证据；
- 每个 P0/P1 候选点至少有 2 条外部相似方案或背景来源；
- 至少能把候选点分流到专利、软著、论文、商业秘密或暂不推进；
- 人工确认问题具体到“能问发明人”的粒度；
- 报告中不包含源码全文、密钥、客户名或敏感数据；
- 报告顶部含查新免责声明（见 §6）；
- 能选择一个专利候选点衔接现有 `patent-disclosure-skill`。

## 14. 风险与防护

| 风险 | 防护 |
| --- | --- |
| AI 编造创新点 | 候选点必须绑定本地证据 |
| 外部检索泄密 | 查询前脱敏，只发送抽象技术短语 |
| 把普通功能误判为专利 | 增加技术性评分和人工确认 |
| 过度相信 web 结果 | 官方/专利/论文来源优先，普通网页只作辅助 |
| 软著材料虚构 | 只从真实项目抽取，不生成伪源码 |
| 论文点空泛 | 必须有实验、数据、对比或方法论 |
| 与现有专利撰写工具同质化 | 保持 discovery-first，不把撰写作为主卖点 |
| 重复刷出已申报/已交底的点 | Step1 吃进已有 IP 材料目录做去重 |
| 评分被当成授权概率/可专利性结论 | 字段改名 `priority_score`，全程仅用于排序，报告含免责声明 |
| web 未命中被误读为"具备新颖性" | 报告顶部强制声明：不构成查新/新颖性意见，正式查新走专利数据库 |

## 15. 推荐实施顺序

### Phase 1：离线挖掘

实现 repo 扫描、候选点生成、Opportunity Card、机会评估报告。

### Phase 2：web 证据层

接入 Tavily/Exa/web search，增加脱敏查询规划、来源归并、相似方案矩阵。

### Phase 3：人工确认闭环

生成确认表，支持推进、合并、否决、改走其他路径。

### Phase 4：分支材料衔接

专利衔接现有交底书 skill；软著和论文分支分别生成材料清单和草案。

## 16. 当前决策建议

建议先做 `ip-opportunity-miner`，不要先做完整专利撰写工具。

第一版的目标不是“生成一份漂亮材料”，而是让研发负责人和 IPR 能坐下来讨论：

- 哪些东西可能值得申请；
- 证据在哪里；
- 与公开方案的区别是什么；
- 还缺哪些确认；
- 下一步走专利、软著、论文还是保密。

这条路线避开了 AI 专利撰写红海，也更贴近研发项目里真正缺失的前置判断能力。
