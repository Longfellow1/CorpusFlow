## 1. 设计判决

复赛 UI 不做完整评测平台，也不做 8 步 wizard。

推荐方案是：

```text
一个 Evaluation Workspace，
把 badcase / eval failure 上传后的“系统理解、问题概览、质量报告、资产包生成”放在同一条视线上。
```

评委现场只需要记住两个对象：

```text
输入：失败证据
输出：数据资产包
```

页面中可以出现“问题族、质量报告、provenance”，但它们都是解释系统如何从输入走到输出的证据，不作为第三、第四个产品心智讲给评委。

## 2. 评审目标

这份稿子先解决四个问题：

1. 10 分钟现场能否讲清楚。
2. 页面是否证明 CorpusFlow 不是 GPT 文本改写器。
3. 评测模式是否承接现有批量生成能力，而不是推翻前两个能力。
4. UI 是否能支撑 PPT 截图和现场降级。

评审时优先看：

- 主链路是否够短。
- 页面上最突出的对象是否是“失败证据”和“资产包”。
- 质量报告是否足够支撑 PPT 量化表达。
- 资产包是否看起来像可复用工程资产，而不是一组临时生成文本。

## 3. 三种 UX 方案取舍

### 3.1 方案 A：单屏 Evidence-to-Asset 工作台

这是推荐方案。

用户上传 badcase 表后，系统自动进入分析态，在同一屏展示：

- 材料理解。
- 问题概览。
- 质量报告。
- 生成资产包按钮。

生成完成后，同一屏右侧或下方展示资产包结构、样例和导出入口。

优点：

- 动作少，适合复赛。
- 截图强，PPT 能直接复用。
- 可以自然表达“系统读懂了证据，再产出数据资产”。
- 实现上能复用 Quick Task 的导入、生成、导出能力。

代价：

- P0 的人工调整能力较弱。
- 后续复杂审阅需要进入 P1。

### 3.2 方案 B：多步 Wizard

流程是：

```text
上传 -> 字段确认 -> badcase 发现 -> 问题族确认 -> 修复策略 -> 生成 -> 导出
```

优点：

- 完整产品解释更细。
- 后续真实工作流更容易扩展审阅、合并、拆分等动作。

代价：

- 10 分钟演示动作太多。
- 评委容易记成“一个复杂表格清洗工具”。
- 截图不够集中，PPT 叙事被拆碎。

复赛不采用。

### 3.3 方案 C：Agent Chat 入口

流程是：

```text
上传证据 -> 与 agent 对话 -> agent 推荐修复计划 -> 用户确认生成
```

优点：

- 更接近长期 agent 叙事。
- 能弱化固定表格 workflow。

代价：

- 现场不稳定，容易变成“又一个 GPT 对话框”。
- 解释成本高，评委难以在短时间确认输出契约。
- 与当前代码结构距离较远。

复赛不采用完整 chat。只保留“自动任务活动流”，表达系统在自主完成读取、归类、生成和打包。

## 4. 主演示路径

### 4.1 操作路径

```text
动作 1：进入“评测增强 / Badcase 回流”
动作 2：上传文件或点击“使用复赛样例”
系统自动：材料理解 + 问题概览 + 质量报告
动作 3：点击“生成修复数据资产包”
系统自动：生成 eval cases / training candidates / provenance
动作 4：展示资产包，导出 JSONL / JSON
```

如果复赛现场需要更稳，可以把动作 2 改成直接点击“使用复赛样例”。

### 4.2 讲解路径

讲解词对应页面区域：

```text
这不是让模型再造几句话。
左边是失败证据，系统先识别哪些行是真失败、哪些缺字段、哪些要拒识。
中间是 CorpusFlow 对失败结构的理解：问题族和质量报告。
右边是一键生成的数据资产包，里面同时有回归评测用例、训练候选和 provenance。
```

### 4.3 成功画面

复赛最重要的完成态截图应该同时出现：

- 文件名和原始样本数。
- “我识别到...”材料理解摘要。
- 3-5 个问题族。
- 质量报告数字。
- `corpusflow_eval_asset/` 资产包树。
- 1 条 eval case 样例。
- 1 条 training candidate 样例。
- `provenance` 来源字段。

## 5. 信息架构

### 5.1 顶层导航

首页卡片从两个变为三个：

```text
精调生成
深度解析、仿写、扩写，适合高价值 seed。

批量任务
弱编辑、重吞吐，适合普通 seeds 批量生成。

评测增强 / Badcase 回流
上传失败证据，生成下一轮回归评测和训练候选资产。
```

评测增强卡片应成为复赛默认入口。比赛演示可以直接打开该入口，不必先解释首页。

### 5.2 工作台对象

P0 只显式展示两个顶层对象：

| 对象 | 页面名称 | 用户理解 |
| --- | --- | --- |
| 失败证据 | Evidence In | 用户上传的 badcase、评测失败、反馈表 |
| 数据资产包 | Asset Out | 可导出的 eval / training / provenance 包 |

中间对象作为系统能力展示：

| 中间能力 | 页面表达 | 不要怎么讲 |
| --- | --- | --- |
| 材料理解 | “我读懂了什么”摘要 | 不讲成字段映射工具 |
| 问题族 | “主要失败结构”卡片 | 不讲成用户要维护的 cluster 对象 |
| 质量报告 | 指标面板 | 不讲成完整 eval report 平台 |
| 任务活动流 | 系统自动完成的步骤 | 不讲成聊天 agent |

## 6. 页面一：入口态

### 6.1 目标

让用户知道自己不是来做普通批量扩写，而是来处理失败证据。

### 6.2 桌面线框

```text
┌────────────────────────────────────────────────────────────────────────────┐
│ CorpusFlow                                           任务列表 / 用户状态     │
├────────────────────────────────────────────────────────────────────────────┤
│                                                                            │
│  ┌──────────────────────┐ ┌──────────────────────┐ ┌────────────────────┐ │
│  │ 精调生成             │ │ 批量任务             │ │ 评测增强 / Badcase │ │
│  │ 高价值 seed 深加工   │ │ 普通 seeds 批量生成  │ │ 回流               │ │
│  │                      │ │                      │ │ 失败证据 -> 数据资产│ │
│  │ 进入                 │ │ 进入                 │ │ 进入               │ │
│  └──────────────────────┘ └──────────────────────┘ └────────────────────┘ │
│                                                                            │
│  最近任务                                                                  │
│  vehicle_agent_badcases_finals.csv   评测增强   已生成 140 条资产          │
│                                                                            │
└────────────────────────────────────────────────────────────────────────────┘
```

### 6.3 UI 文案

卡片标题：

```text
评测增强 / Badcase 回流
```

卡片说明：

```text
上传评测失败、badcase 表或用户反馈，生成下一轮回归评测和训练候选数据。
```

任务标签：

```text
失败证据
数据资产包
可追溯
```

### 6.4 视觉要求

- 入口卡片颜色使用 amber + emerald：amber 表示失败证据，emerald 表示输出资产。
- 不用大段说明文字。
- 不把“评测模式”说成“新平台”，避免范围变大。

## 7. 页面二：导入态

### 7.1 目标

让用户以最低成本把证据放进来，并看见系统“不要求固定模板”。

### 7.2 桌面线框

```text
┌────────────────────────────────────────────────────────────────────────────┐
│ 评测增强 / Badcase 回流                                  保存 / 导出       │
├───────────────────────┬────────────────────────────────────────────────────┤
│ Evidence In           │                                                    │
│                       │  ┌──────────────────────────────────────────────┐  │
│ 上传失败证据           │  │ 将 badcase / eval failure 放进来              │  │
│ ┌───────────────────┐ │  │                                              │  │
│ │ 拖拽 CSV/XLSX/JSON │ │  │ 支持评测失败表、测试记录、用户反馈和备注。     │  │
│ │ 或点击选择文件     │ │  │ 不要求先整理成固定模板。                     │  │
│ └───────────────────┘ │  │                                              │  │
│                       │  │ [选择文件]  [使用复赛样例]                   │  │
│ 最近使用              │  └──────────────────────────────────────────────┘  │
│ vehicle_agent...csv   │                                                    │
│                       │  右侧空态：等待失败证据进入                         │
└───────────────────────┴────────────────────────────────────────────────────┘
```

### 7.3 用户动作

P0 保留两个动作：

- 选择文件。
- 使用复赛样例。

“粘贴文本”“连接 Langfuse / promptfoo”只作为 P1/P2 能力，不进入复赛主界面。

### 7.4 导入后反馈

导入完成后不要只显示字段映射。第一反馈必须是系统理解：

```text
我识别到这是一份车载助手 badcase 表，共 42 行。
已抽取 39 个候选 case，其中 31 个是明确失败，7 个缺少 expected，可作为弱诊断样本。
主要字段已识别为：用户问题、期望行为、实际回答、失败备注、通过状态。
```

### 7.5 状态设计

| 状态 | 视觉 | 文案 |
| --- | --- | --- |
| 空态 | 上传区域居中 | 将 badcase / eval failure 放进来 |
| 解析中 | 进度条 + 活动流 | 正在读取字段、抽取失败证据 |
| 可分析 | 自动跳转到理解视图 | 已抽取候选 case |
| 解析失败 | amber/rose 提示 | 文件解析失败，可使用复赛样例继续演示 |
| 降级 | 顶部细提示条 | 已切换到内置复赛样例 |

## 8. 页面三：分析完成态

### 8.1 目标

这是复赛核心画面。页面必须证明：

```text
CorpusFlow 读懂了失败证据，而不是只读取了表头。
```

### 8.2 桌面线框

```text
┌────────────────────────────────────────────────────────────────────────────┐
│ 评测增强 / Badcase 回流       vehicle_agent_badcases_finals.csv   Ready   │
├───────────────────────┬───────────────────────────────────────┬────────────┤
│ Evidence In           │ Analysis                              │ Action     │
│                       │                                       │            │
│ 文件                   │ ┌───────────────────────────────────┐ │ 任务活动流  │
│ vehicle_agent...csv   │ │ 我读懂了什么                       │ │ ✓ 读取文件  │
│ 42 行 / 39 case       │ │ 车载助手 badcase 表，31 个明确失败 │ │ ✓ 抽取 case │
│ 拒识 3                │ │ 主要字段：query/expected/actual... │ │ ✓ 识别问题族│
│                       │ └───────────────────────────────────┘ │            │
│ 字段角色              │                                       │ 主按钮      │
│ 用户问题 query        │ ┌───────────────┐ ┌────────────────┐ │ [生成修复   │
│ 期望 expected         │ │ 主要失败结构   │ │ 质量报告       │ │  数据资产包]│
│ 实际 actual           │ │ 复合约束遗漏   │ │ 明确失败 31    │ │            │
│ 状态 passed           │ │ 多轮承接失败   │ │ 有效样本 39    │ │ 输出预估    │
│                       │ │ 工具选择错误   │ │ 字段识别 91%   │ │ eval 56    │
│ 样例 case             │ │ 安全边界回答   │ │ 问题族 5       │ │ train 84   │
│ #018                  │ └───────────────┘ └────────────────┘ │            │
└───────────────────────┴───────────────────────────────────────┴────────────┘
```

### 8.3 布局比例

桌面建议使用三栏：

| 区域 | 宽度 | 作用 |
| --- | --- | --- |
| 左栏 Evidence In | 280-320px | 文件、字段角色、代表 case |
| 中央 Analysis | 自适应 | 材料理解、问题族、质量报告 |
| 右栏 Action | 280-340px | 活动流、主按钮、输出预估、降级提示 |

这样能沿用当前 Quick Task 的“左侧控制 + 中央结果”模式，但把右侧行动区补出来，让复赛画面更像一个 agent 正在组织任务。

### 8.4 左栏：Evidence In

内容顺序：

1. 文件卡片。
2. 样本统计。
3. 字段角色。
4. 代表 badcase。
5. 重传 / 使用样例。

示例：

```text
vehicle_agent_badcases_finals.csv
42 行原始记录
39 个候选 case
31 个明确失败
3 个安全拒识
```

字段角色显示：

```text
用户问题       query
期望行为       expected
实际回答       actual
失败备注       note
通过状态       passed
```

代表 badcase：

```text
#018
用户：我快没油了，找一个顺路、不下高速、评分高的加油站
期望：说明可行加油站、绕行成本和是否需要下高速
实际：推荐附近加油站，但没有判断是否顺路
```

### 8.5 中央上区：我读懂了什么

这一区是复赛最重要的“不是 GPT 前端”证明。

标题：

```text
我读懂了什么
```

摘要：

```text
这批样本主要来自车载助手测试失败记录。失败集中在复合约束遗漏、多轮上下文承接和工具选择错误。
31 条样本包含明确 expected / actual 对比，可直接构造回归评测；7 条缺少 expected，只进入 silver training candidate。
```

证据完整度：

```text
证据完整度 82%
可完整诊断 31
需人工确认 7
拒识 3
```

### 8.6 中央中区：主要失败结构

不要把 `ProblemCluster` 当工程对象讲给评委。页面文案叫：

```text
主要失败结构
```

卡片字段：

```text
名称
样本数
失败机制
代表 badcase
修复方向
建议资产
```

示例卡片：

```text
复合约束遗漏
12 cases
失败机制：回答只满足部分约束，遗漏顺路、评分、绕行成本等条件。
代表 badcase：#018 找顺路不下高速的加油站
修复方向：补充多约束 expected behavior 和 eval points。
建议资产：eval cases + instruct candidates
```

推荐 P0 展示 5 张卡：

- 复合约束遗漏。
- 多轮上下文承接失败。
- 落域 / 工具选择错误。
- 弱答或空泛回答。
- 安全拒识与边界回答。

### 8.7 中央右区：质量报告

质量报告服务于 PPT。指标要少而有解释力。

建议首屏指标：

```text
原始样本       42
候选 case      39
明确失败       31
需确认样本      7
安全拒识        3
字段识别成功率 91%
问题结构        5
预计产出        140
```

二级指标：

```text
证据完整度      82%
可直接回归      31
可生成 silver   7
预计节省整理时间 3.5h
```

视觉表达：

- 数字卡片使用紧凑网格。
- `明确失败`、`问题结构`、`预计产出`三个数字要最大。
- 不用复杂图表，P0 用条形占比即可。

### 8.8 右栏：任务活动流

为了兼顾“agent 感”，右栏展示自动完成的任务活动，而不是聊天框。

示例：

```text
CorpusFlow Agent
✓ 读取 42 行原始记录
✓ 抽取 39 个 Evidence Case
✓ 识别 5 类主要失败结构
✓ 生成修复数据计划
待执行：生成资产包
```

活动流约束：

- 只展示事实动作，不展示长推理。
- 每条 1 行，最多 6 条。
- 失败时显示可解释错误和降级动作。

右栏主按钮：

```text
生成修复数据资产包
```

按钮下方输出预估：

```text
预计生成
56 条回归评测样本
84 条训练候选样本
1 份 provenance
1 份 quality report
```

## 9. 页面四：生成中

### 9.1 目标

让现场知道系统没有卡死，并让降级切换自然发生。

### 9.2 线框

```text
┌────────────────────────────────────────────────────────────────────────────┐
│ 生成修复数据资产包                                         62%             │
├────────────────────────────────────────────────────────────────────────────┤
│ ✓ 将问题结构转成生成计划                                                   │
│ ✓ 生成回归评测样本                                                         │
│ → 生成训练候选样本                                                         │
│   写入 provenance                                                          │
│   生成质量报告                                                             │
│                                                                            │
│ [暂停] [使用预生成结果继续]                                                 │
└────────────────────────────────────────────────────────────────────────────┘
```

### 9.3 生成阶段

```text
Step 1：生成计划
Step 2：eval cases
Step 3：training candidates
Step 4：provenance
Step 5：quality report
```

### 9.4 降级机制

超过 8 秒没有生成结果时，右栏出现轻提示：

```text
模型服务响应较慢，可使用预生成复赛结果继续展示。
```

按钮：

```text
使用预生成结果继续
```

点击后仍进入同一个资产包页面，不切换到另一套 demo。

## 11. PPT 截图规划

PPT 不等 UI 完成后再补。UI 从一开始就按截图服务。

### 11.1 必备截图

| 截图 | 页面 | PPT 用途 |
| --- | --- | --- |
| S1 | 导入态 | 证明输入是 messy failure evidence |
| S2 | 分析完成态 | 证明系统读懂证据 |
| S3 | 问题结构 + 质量报告 | 证明 badcase 被归纳成可行动问题 |
| S4 | 资产包完成态 | 证明输出是可导出数据资产 |

### 11.2 PPT 页面对应

```text
P1：企业 AI 应用上线后，失败证据无法进入下一轮改进
P2：CorpusFlow 的位置：failure evidence -> dataset asset
P3：复赛场景：车载助手 badcase 回流
P4：Demo 主链路截图：上传 -> 理解 -> 生成 -> 资产包
P5：系统理解和质量报告截图
P6：资产包截图
P7：开源方向：Trace-to-Dataset Pipeline
```

### 11.3 讲解中的数字

PPT 和 UI 必须使用同一组数字：

```text
42 行原始记录
39 个候选 case
31 个明确失败
5 类主要失败结构
56 条回归评测样本
84 条训练候选样本
140 条总资产
82% 证据完整度
```

这些数字可以来自 demo 数据，不需要成为真实线上指标。

## 12. 视觉风格

### 12.1 总体风格

沿用现有 CorpusFlow 深色工作台，不重做品牌。

关键词：

```text
专业、密集、可扫描、数据资产感
```

避免：

- 营销站式 hero。
- 大面积渐变背景。
- 纯聊天界面。
- 过多解释文字。
- 多层卡片套卡片。

### 12.2 色彩

建议：

| 用途 | 颜色倾向 | 含义 |
| --- | --- | --- |
| 背景 | slate / near-black | 工作台底色 |
| 失败证据 | amber | 输入、警示、待确认 |
| 数据资产 | emerald | 输出、可导出、完成 |
| 系统分析 | sky | 理解、诊断、质量报告 |
| 拒识 / 错误 | rose | 不可用、失败 |

不要让页面只剩 emerald 或 purple。评测模式需要同时看到“失败”和“资产”的转换。

### 12.3 字体与密度

- 页面标题：18-20px。
- 区块标题：13-14px。
- 指标数字：22-28px。
- 样例数据：12-13px，等宽字体。
- 卡片圆角：8px 为主，避免大圆角造成玩具感。
- 表格和指标优先可扫描，不做大段说明。

### 12.4 图标

后续实现优先使用 lucide：

| 对象 | 图标 |
| --- | --- |
| 上传 | `Upload` |
| 文件 | `FileText` |
| 分析 | `ScanSearch` 或 `Activity` |
| 问题结构 | `Network` |
| 质量报告 | `BarChart3` |
| 资产包 | `PackageCheck` |
| 导出 | `Download` |
| 降级 | `ShieldAlert` |

## 13. 关键交互细节

### 13.1 自动分析

上传成功后自动开始分析，不让用户再点“开始分析”。

理由：

- 复赛减少动作。
- 产品心智是 agent 自动读证据。
- 用户真正需要决策的是是否生成资产包。

### 13.2 主按钮只有一个

分析完成态的主按钮只保留：

```text
生成修复数据资产包
```

不要在 P0 同时出现：

- 选择问题族。
- 选择输出比例。
- 选择生成模式。
- 配置模型参数。

这些会把演示拉回工作台配置工具。

### 13.3 问题族只读

P0 问题族卡片只读展示。点击可展开代表 badcase，但不提供合并、拆分、重命名。

理由：

- 比赛现场不需要展示人工维护 cluster。
- 先证明系统能归纳问题。
- 后续 P1 再补审阅编辑。

### 13.4 资产样例可切换

完成态使用 tabs：

```text
Eval Cases
Training Candidates
Quality Report
Provenance
```

默认打开 `Eval Cases`。切到 `Provenance` 时要能看到来源文件、行号、case id。

### 13.5 导出按钮

P0 导出按钮：

```text
JSONL
JSON
CSV
```

页面可以有“导出资产包”主按钮，但 P0 不承诺真实 zip。点击后可以导出当前选中的 JSON / JSONL，或显示可导出清单。

## 14. 现场降级 UI

### 14.1 健康状态

页面右上角保留一个小状态，不抢主叙事：

```text
服务正常
```

异常时：

```text
模型服务较慢，已准备复赛样例结果
```

### 14.2 降级触发

页面逻辑：

```text
导入分析超过 3 秒 -> 允许使用内置样例结果
资产生成超过 8 秒 -> 允许使用预生成资产包
服务健康检查失败 -> 默认进入样例演示
```

### 14.3 降级文案

顶部提示：

```text
已切换到内置复赛样例，页面结构和导出内容与正常流程一致。
```

不要写：

```text
Demo 模式
假数据
备用页面
```

## 15. P0 与 P1 边界

### 15.1 P0 必须做

- 首页或直接路由能进入评测增强。
- 上传文件或使用复赛样例。
- 自动显示材料理解摘要。
- 显示字段角色、样本统计、拒识数量。
- 显示 3-5 个主要失败结构。
- 显示质量报告指标。
- 一键生成修复数据资产包。
- 展示资产包树和样例。
- 展示 provenance 来源信息。
- 支持 JSON / JSONL / CSV 的可见导出入口。
- 支持预生成结果降级。

### 15.2 P1 再做

- 问题族筛选。
- 修复目标选择。
- 输出比例配置。
- 问题族合并 / 拆分 / 重命名。

- 粘贴文本入口。
- 审阅队列。

### 15.3 P2 再做

## 16. 可用性检查

### 16.1 5 秒理解测试

把完成态截图给陌生人看 5 秒，对方应能复述：

```text
这是把失败案例变成训练和评测数据包的工具。
```

如果对方说成：

```text
这是一个表格上传工具
这是一个批量生成工具
这是一个评测报表工具
```

说明主视觉需要继续收敛。

### 16.2 10 分钟演示测试

演示中不得依赖口头补偿解释以下内容：

- 输入是什么。
- 系统读懂了什么。
- 为什么这些问题值得修。
- 输出能用于哪里。
- 每条资产来自哪里。

这些必须在页面上可见。

### 16.3 GPT 替代测试

页面必须显式证明 GPT 聊天窗口缺少的能力：

| GPT 可做 | CorpusFlow 必须多做 |
| --- | --- |
| 改写 badcase | 保留 source row / case id |
| 总结失败 | 形成问题结构和质量报告 |
| 生成样本 | 输出 eval / training / provenance 多文件资产包 |
| 给建议 | 形成可导出契约 |

## 17. 待评审问题

请优先评审这 6 个点：

1. 单屏工作台是否足够有冲击力，还是需要更强的 asset package 视觉。
2. 右栏“任务活动流”是否足够 agentic，还是仍然太像普通 workflow。
3. “问题族”在页面上是否应该叫“主要失败结构”，避免工程味过重。
4. 资产包树是否能让评委一眼理解输出价值。
5. 质量报告的数字是否足够支撑 PPT。
6. 首页是否需要保留三个入口，还是复赛版本直接打开评测增强。

## 18. 下一步建议

评审通过后，下一步不是直接做完整实现，而是先画一个低保真静态页面或本地 mock：

```text
mock route: /evaluation-demo
data source: 内置复赛样例 JSON
goal: 1 个完成态页面先能截图进 PPT
```

等完成态截图确认后，再补导入态、生成中和降级态。
