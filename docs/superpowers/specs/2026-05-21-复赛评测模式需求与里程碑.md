日期：2026-05-21

UX / UI 设计稿：

```text
docs/superpowers/specs/2026-05-21-evaluation-mode-ux-ui-draft.md
```

## 1. 项目负责人判断

当前阶段最高 POI 是：

```text
把“失败证据 -> 评测/训练数据资产”的复赛演示链路做完整、稳定、直观。
```

不是做完整评测平台，不是做 CLI，不是做外部 adapter，也不是重构全部产品。

用户已确认：

- 演示数据可以从 `migration_package` 抽，也可以自造，数据不是卡点。
- 当前核心是从比赛交互流程反推功能点，优先做可演示工作台，而不是 CLI。
- 质量报告不复杂，但必须成为 PPT 的量化证据。
- 组合资产包直观说明问题即可，不必先追求真实 zip 工程化。
- PPT 视觉设计最后做，但故事板必须前置；大事业叙事要进入 PPT，但不能压过现场主链路。

因此，复赛阶段的产品定义是：

```text
评测模式 P0 = badcase / eval failure 文件进入 CorpusFlow 后，
自动生成材料理解、问题概览、质量报告、评测用例和训练候选数据包。
```

外部评审后，复赛阶段再收紧三条原则：

1. 演示动作少于功能完整度。主链路必须压到 4 个动作以内。
2. 评委只需要记住两个对象：输入是失败证据，输出是数据资产包。
3. PPT 故事板与产品实现并行启动，不能等功能做完再包装。

## 2. 目标与非目标

### 2.1 复赛目标

在 10 分钟现场演示中证明：

1. CorpusFlow 解决的是 AI 应用上线后 badcase 难以回流的问题。
2. 系统能把失败证据读懂，并转成下一轮训练和回归评测数据。
3. 输出不是临时文本，而是可复核、可导出、可追溯的数据资产。
4. 现有 QA / instruct / multi-turn 生成能力没有被颠覆，而是成为评测修复流程里的执行器。

### 2.2 非目标

复赛前不做：

- 完整 Eval Runner。
- LLM Judge。
- CI Gate。
- Langfuse / Phoenix / Opik adapter。
- CLI / SDK。
- 真实训练闭环。
- 复杂 trace reconstruction。
- 大规模 UI 重构。

## 3. 产品交互主线

复赛演示必须围绕一个连续工作流，而不是功能点罗列。

```text
导入 badcase / eval failure 样例
-> 一屏展示“我读懂了什么” + 问题概览 + 质量报告
-> 一键生成 eval cases / training candidates 资产包
-> 展示资产包内容、来源和用途
```

评测增强入口可以存在，但复赛主演示不要把“选择评测模式”作为一个需要讲解的动作。问题族筛选、修复目标选择可以作为产品能力保留，但不进入 10 分钟主路径。

### 3.1 入口

首页或任务工作区中要能明确看到：

```text
评测增强 / Badcase 回流
```

入口文案：

```text
上传评测失败、badcase 表或用户反馈，生成下一轮回归评测和训练候选数据。
```

### 3.2 材料理解

上传样例后，页面不应只展示字段映射，而应展示系统理解摘要：

```text
我识别到这是一份车载助手 badcase 表，共 42 条记录。
其中 31 条为明确失败，7 条缺少 expected，可作为弱诊断样本。
主要字段已识别为：用户问题、期望行为、实际回答、失败备注、通过状态。
```

功能要求：

- 识别原始样本数。
- 识别有效样本数。
- 识别 rejected / sensitive 样本数。
- 展示字段角色映射。
- 展示证据完整度等级。

### 3.3 问题概览

系统在质量报告区域展示 3-5 个问题族。比赛叙事中不要把 `ProblemCluster` 作为第三个顶层对象讲给评委，工程实现可以保留，前端表达应把它收进“系统如何理解失败证据”的可视化里。

比赛 P0 不要求真实复杂聚类，可使用规则和样例数据结构生成稳定结果。关键是让评委看懂“系统不是在造句，而是在归纳问题”。

问题族卡片字段：

```text
问题族名称
失败机制
样本数
代表 badcase
失败信号
修复方向
建议生成资产
```

建议内置问题族：

- 复合约束遗漏。
- 多轮上下文承接失败。
- 落域 / 工具选择错误。
- 弱答或空泛回答。
- 安全拒识与边界回答。

### 3.4 质量报告

质量报告是 PPT 量化证明的主要来源。

页面指标：

```text
原始样本数
有效样本数
明确失败数
疑似失败数
拒识样本数
字段识别成功率
问题族数量
生成 eval case 数
生成 training candidate 数
预计节省人工整理时间
```

质量报告可以先由前端基于样例和生成结果计算，不要求复杂后端。

### 3.5 修复数据生成

复赛主路径中，用户不需要逐个选择修复目标。系统在问题概览后提供一个主按钮：

```text
生成修复数据资产包
```

底层复用现有生成能力：

- QA 生成用于 eval query / expected behavior。
- instruct 生成用于训练候选。
- multi-turn 生成用于上下文承接类问题。

产品表达上要改名：

```text
不是“批量生成样本”
而是“基于问题族生成修复数据”
```

问题族筛选、资产类型选择可以放入 P1。P0 优先保证“导入后直接生成完整资产包”的演示稳定性。

### 3.6 资产包展示

不要求 P0 真实 zip，但页面必须清楚展示资产包内容。

```text
corpusflow_eval_asset/
  eval_cases.jsonl
  training_candidates.jsonl
  rejected_cases.csv
  quality_report.json
  provenance.json
```

每类资产展示 1-2 条样例。

`provenance` 至少包含：

```text
source_file
source_row
source_case_id
problem_cluster
asset_type
generated_at
```

### 3.7 现场降级预案

复赛演示必须默认网络、模型服务、冷启动都有可能出问题。P0 需要准备可见但不打扰主流程的兜底能力。

触发条件：

- 导入后超过 3 秒没有进入理解报告。
- 生成资产包超过 8 秒没有结果。
- 模型或算法接口返回错误。
- 线上服务健康检查失败。

切换动作：

```text
使用内置复赛样例
-> 读取预生成理解报告和资产包
-> 页面继续展示同一条主演示链路
```

兜底结果必须和正常链路使用同一套页面结构，避免现场看起来像切到另一套 demo。

## 4. 架构师判断

### 4.1 当前实现复用原则

当前项目已有稳定能力：

- 快速任务导入。
- 字段识别。
- 敏感拒识。
- QA / instruct / multi-turn 生成。
- 进度展示。
- JSON / CSV / JSONL 导出。

评测模式 P0 不应重写这些能力。

推荐做法：

```text
新增 Evaluation Mode 的数据对象和 UI 编排
复用 Quick Task 的导入、生成和导出能力
把现有生成结果包装成 eval asset package
```

### 4.2 建议模块边界

前端 P0 可新增三个纯函数模块：

```text
evalEvidenceImport
  输入 quick rows / demo rows
  输出 EvalEvidenceCase[]

evalProblemMining
  输入 EvalEvidenceCase[]
  输出 ProblemCluster[] + QualityReport

evalAssetPackage
  输入 ProblemCluster[] + generated items
  输出 EvalAssetPackage
```

这些模块应先用确定性规则和样例数据跑通，不依赖不稳定模型链。

后端 P0 可暂不新增复杂接口。已有 `/api/algorithm/quick-generate` 和 `/api/tasks/:taskId/export` 可继续承担生成和导出。

### 4.3 核心数据对象

#### EvalEvidenceCase

```json
{
  "id": "case_001",
  "query": "我快没油了，帮我找顺路加油站，不要绕太远",
  "expected": "推荐顺路加油站，并说明绕行成本",
  "actual": "为你推荐附近加油站",
  "passed": false,
  "failureNote": "遗漏顺路约束和绕行成本",
  "category": "车载助手",
  "source": {
    "fileName": "demo_badcases.csv",
    "rowId": "12"
  }
}
```

#### ProblemCluster

`ProblemCluster` 是内部过程对象，不在 PPT 和主演示中作为独立概念展开。前端可以将它表达为质量报告里的“问题族分布 / 代表 badcase / 修复方向”。

```json
{
  "id": "cluster_constraint_missing",
  "name": "复合约束遗漏",
  "caseCount": 12,
  "pattern": "Semantic / multi-intent",
  "failureSignals": ["主意图正确", "遗漏附加约束", "缺少解释依据"],
  "repairDirection": "补充多约束、多目标、需要解释依据的训练与回归样本"
}
```

#### EvalAssetPackage

```json
{
  "evalCases": [],
  "trainingCandidates": [],
  "rejectedCases": [],
  "qualityReport": {},
  "provenance": []
}
```

## 5. 产品功能需求

### P0 必须完成

1. 评测增强入口，但主演示可直接进入导入页。
2. 内置复赛样例数据。
3. 上传 / 导入 badcase 表后一屏展示材料理解摘要、字段角色、证据完整度。
4. 在同一屏展示 3-5 个问题族、代表 badcase 和质量报告指标。
5. 一个主动作生成 eval cases / training candidates 资产包。
6. 展示资产包结构、样例内容、来源和用途。
7. 支持导出 JSON / JSONL，至少能导出 eval cases 和 training candidates。
8. 准备预生成结果和现场兜底切换路径。
9. 准备 PPT 所需截图、故事板和演示录屏路径。

### P1 可选增强

1. 问题族筛选和修复目标选择。
2. 每个问题族展开更多代表 case。
3. `provenance.json` 单独导出。
4. 资产包伪 zip 或多文件下载。
5. 更精致的质量报告页面。

### P2 不进复赛

1. 真实 LLM 辅助聚类。
2. Langfuse / Phoenix adapter。
3. CLI。
4. review queue。
5. artifact rebuild / diff。
6. 真实训练后效果回填。

### 5.4 成功指标

复赛阶段不用追求平台指标，先用演示指标约束开发。

必须达成：

1. 5 分钟内从导入展示到理解报告、问题族和质量报告。
2. 10 分钟内讲完完整链路，不需要口头补救产品缺口。
3. 任一步骤失败后，30 秒内切换到预生成结果并继续演示。
4. 2-3 个不熟悉项目的人看完后，能复述“失败证据进入，数据资产包出来”。
5. PPT、页面文案、资产包字段使用同一套词：失败证据、理解报告、质量报告、数据资产包、provenance。

不作为 P0 成功指标：

- zip 下载是否完整工程化。
- adapter 是否能接入真实外部平台。
- CLI 是否可用。
- 聚类是否由 LLM 自动完成。
- 导出格式是否覆盖所有下游训练平台。

## 6. 里程碑

### M0：方向封口

时间：2026-05-21

产出：

- 大事业叙事文档。
- 复赛评测模式需求与里程碑。
- 明确最高 POI：评测模式演示链路。

验收：

- 团队不再围绕“完整评测平台 / CLI / adapter”发散。
- PPT 主叙事和产品实现方向一致。

### M1：演示故事板、样例数据与数据对象

时间：2026-05-22

产出：

- 5 页 PPT 故事板草稿，不做视觉美化，只锁定叙事顺序。
- 4 步主演示脚本：导入、理解报告、生成资产包、展示资产包。
- 复赛 badcase / eval failure 样例数据。
- `EvalEvidenceCase`、`ProblemCluster`、`EvalAssetPackage` 数据结构。
- 可从样例数据生成质量报告和问题族。
- 现场兜底预案草稿：兜底触发条件、切换动作、预生成数据来源。

- 样例能覆盖车载助手、弱答、约束遗漏、安全拒识、多轮上下文。
- 5 页故事板能讲清楚“失败证据 -> 数据资产包”，不依赖功能细节堆叠。

## 7. PPT 设计方向

PPT 应先讲复赛可见价值，再在结尾抬高大事业。故事板必须从 M1 开始迭代，M4 只做成稿、美化和录屏。

建议页结构：

1. 标题：让每一次 badcase 成为下一轮 AI 能力提升的数据资产。
2. 问题：企业 AI 应用上线后，失败证据散落，难以回流。
3. 旧流程：人工读日志、整理表格、补 expected、写 eval points。
4. CorpusFlow：失败证据到评测/训练数据资产的闭环。
5. Demo 主线：上传 badcase -> 理解报告 -> 一键生成 -> 资产包。
6. 技术方案：字段识别、拒识、问题族归纳、生成执行器、provenance。
7. 量化收益：整理时间、样本规模、保留率、导出格式。
8. 复用场景：座舱、售后、测试、知识库、研发 Agent。
9. 大事业：Trace-to-Dataset Pipeline。
10. 总结：评测不是终点，失败证据是模型持续变好的燃料。

## 8. 风险与应对

| 风险 | 应对 |
| --- | --- |
| 评测模式做太大 | P0 主路径压成 4 个动作，不做 CLI / adapter |
| 现场模型不稳定 | 内置样例和预生成结果兜底，明确超时切换动作 |
| 页面像普通生成工具 | 强化材料理解、质量报告、资产包三个核心视觉锚点 |
| 演示动作过密 | 主演示不讲评测模式选择和修复目标选择 |
| 评委记不住对象 | 叙事只暴露“失败证据”和“数据资产包”两个对象 |
| PPT 与产品脱节 | M1 同步产出故事板，M4 只做成稿和录屏 |
| 叙事过大被问穿 | 明确复赛是 Trace-to-Dataset 的第一段切片 |
| 输出不够工程化 | 展示 asset package 和 provenance |

## 9. 最终项目负责人结论

复赛前所有投入围绕一个问题排序：

```text
这件事是否能让评委在 10 分钟内相信：
CorpusFlow 不是生成文本的工具，而是把 AI 应用失败证据回流为训练和评测资产的工程系统？
```

能增强这个判断的，优先做。
不能增强这个判断的，复赛后再做。
