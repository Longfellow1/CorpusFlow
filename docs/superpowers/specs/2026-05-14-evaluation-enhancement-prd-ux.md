# CorpusFlow 评测增强模式 PRD + UX

日期：2026-05-14

## 1. 核心判断

评测增强模式不是让用户按固定模板上传评测表，也不是把 Quick Task 换一个名字。

它应该是：

```text
面向 badcase、评测结果、用户反馈和 Agent 运行轨迹的智能证据摄取与数据修复工作流。
```

产品要解决的问题不是“如何校验用户文件是否合规”，而是：

```text
用户手上有一堆混乱的失败证据，CorpusFlow 如何最大限度读懂它们，并把它们转成可诊断、可复核、可生成、可导出的训练与评测资产。
```

因此，上传体验的第一原则是：

```text
系统适应用户材料，而不是用户被迫适应系统模板。
```

如果用户上传的是规范评测表，系统应直接识别。
如果用户上传的是半结构化表格，系统应推断字段和含义。
如果用户上传的是日志、反馈、测试备注或混乱文本，系统应先抽取候选 case。
如果材料确实不足，系统也不应只报错，而应说明“现在能做什么、缺什么会影响什么、如何最少补齐”。

## 2. 一句话定义

```text
CorpusFlow 评测增强模式把任意形态的失败证据，转成问题族诊断、修复策略和下一轮训练 / 回归评测数据资产。
```

复赛口语表达：

```text
企业 AI 应用上线后，badcase 往往散落在评测表、日志、用户反馈和测试备注里。CorpusFlow 不要求用户先整理成标准模板，而是先读懂这些证据，自动抽取失败样本，聚成问题族，再生成下一轮训练和回归评测数据。
```

## 3. 目标用户

### 测试工程师

手上有评测失败表、测试记录、手工 badcase、回归缺口。

核心诉求：

- 不想手工整理字段。
- 想快速知道失败集中在哪几类问题。
- 想快速生成下一轮回归评测集。

### 算法工程师

手上有线上 badcase、离线评测结果、模型版本对比结果。

核心诉求：

- 想把失败样本转成训练候选数据。
- 想保留来源、失败类型和生成配置。
- 想知道哪些失败是语义、检索、工具、上下文或评测覆盖问题。

### 数据 PM / 业务同学

手上有用户反馈、客服记录、业务专家备注。

核心诉求：

- 不想理解训练数据格式。
- 想把业务反馈转成结构化数据任务。
- 想参与确认问题族，而不是从零手写样本。

## 4. 产品边界

### 做

- 接收规范表、半结构化表、日志文本、用户反馈、测试备注。
- 智能理解文件内容，抽取候选 badcase。
- 自动推断字段和证据角色。
- 识别显性和隐性 badcase。
- 基于 Deep Fix 思路抽象失败模式，而不是堆硬规则。
- 将 badcase 聚成问题族。
- 生成诊断卡片和修复策略。
- 将修复策略自然转入批量生成。
- 导出评测数据、训练候选数据、质量报告和诊断资产。

### 不做

- 不运行完整评测任务。
- 不做正式 LLM Judge 平台。
- 不做 CI / 发布 Gate。
- 不做模型训练和自动微调。
- 不声称自动证明真实根因。
- 不要求用户必须使用固定上传模板。

## 5. 智能上传设计

### 5.1 设计原则

传统上传逻辑是：

```text
用户必须提供符合要求的字段 -> 系统才能工作
```

评测增强模式应改成：

```text
用户提供证据材料 -> 系统尽力理解 -> 系统说明可分析等级 -> 用户最小确认 -> 系统继续推进
```

上传入口不展示“字段不合规”的机器式错误，而展示“我从你的材料里读出了什么”。

核心体验应该像：

```text
我识别到这是 37 条车载助手测试记录，其中 18 条明确失败，9 条疑似遗漏约束，6 条缺少 expected，可先进入弱诊断。
```

而不是：

```text
缺少 expected 字段，请重新上传。
```

### 5.2 输入形态

P0 支持：

- CSV。
- 内置样例数据。
- 粘贴表格文本。
- 粘贴多段 badcase 文本。

P1 支持：

- XLSX。
- JSON / JSONL。
- 日志片段。
- Agent trace 摘要。

P0 不要求做复杂文件解析平台，但产品契约必须能表达“任意材料先被理解，再被结构化”。

### 5.3 智能摄取流水线

```text
原始文件
-> 文件形态识别
-> 候选 case 抽取
-> 字段角色推断
-> 证据完整度评估
-> 最小确认
-> 标准 Eval Evidence Case
```

#### 文件形态识别

系统先判断材料像什么：

- 规范评测表。
- 测试 badcase 表。
- 用户反馈列表。
- 客服 / 工单记录。
- 日志摘录。
- 人工备注。
- 混合材料。

这个判断只用于后续解析策略，不要求用户先选择。

#### 候选 case 抽取

即使没有标准字段，也要尝试抽取：

- 用户问题。
- 期望行为。
- 模型实际回答。
- 失败说明。
- 场景分类。
- 来源行号或文本位置。
- 模型版本或系统版本。

系统抽取后展示“候选 case”，而不是要求用户按列名整理。

#### 字段角色推断

字段不等于列名。系统应根据内容语义判断角色。

示例：

| 原始列名 | 可能角色 |
| --- | --- |
| 问题描述 | query / failure_note |
| 标准回复 | expected |
| 实际结果 | actual |
| 是否通过 | passed |
| 备注 | failure_note / expected / error_type |
| 处理意见 | repair_hint |

用户看到的是角色解释，而不是一堆字段名：

```text
“实际结果”看起来是模型回答。
“处理意见”更像人工标注的失败原因。
“备注”里包含一部分期望行为，可以用来补齐 expected。
```

#### 证据完整度评估

用能力等级表达，而不是合规等级表达。

| 等级 | 用户文案 | 系统可做能力 |
| --- | --- | --- |
| A | 可完整诊断 | badcase 判断、失败模式、聚类、修复策略、评测 / 训练数据生成 |
| B | 可弱诊断 | badcase 候选、问题族聚类、silver 数据生成，需要人工确认 expected |
| C | 可整理成数据任务 | 抽取 query 和场景，生成评测候选或训练候选，不能确认真实失败 |
| D | 需要补充关键证据 | 引导用户补 query、expected 或 actual 中的最小必要信息 |

注意：D 级也不是失败页。D 级应给出“补证据卡片”。

### 5.4 最小字段原则

系统内部需要的标准结构：

```json
{
  "sourceCaseId": "string",
  "query": "string",
  "expected": "string",
  "actual": "string",
  "passed": false,
  "score": 0.42,
  "category": "string",
  "errorType": "string",
  "traceId": "string",
  "modelVersion": "string",
  "failureNote": "string",
  "sourceLocation": "row-12"
}
```

但不能把这个结构直接暴露成用户上传要求。

产品上只说明：

```text
至少需要知道“用户问了什么”。
如果有“期望回答”和“实际回答”，系统可以做完整失败诊断。
如果只有“用户问题 + 期望行为”，系统可以生成评测数据。
如果只有“用户问题 + 实际回答”，系统可以发现疑似问题，但需要人工确认是否失败。
```

### 5.5 缺失字段时的智能补齐策略

#### 缺 expected

系统不阻塞，而是：

- 从人工备注中抽取 expected candidate。
- 从同类 case 中归纳 expected behavior。
- 生成 `silver_expected_candidate`。
- 标记“需要人工确认后才能作为 gold/regression”。

#### 缺 actual

系统不做失败诊断，而是：

- 将样本作为评测构造种子。
- 生成 expected behavior 和 eval points。
- 标记“无法判断模型是否失败”。

#### 缺 passed / score

系统用 expected 与 actual 差异做弱判断：

- 是否答非所问。
- 是否遗漏关键约束。
- 是否格式不符。
- 是否过度承诺。
- 是否缺少必要追问。

输出为 `inferredBadcase`，不是正式 `passed=false`。

#### 原始材料是混乱文本

系统先做 case segmentation：

```text
这段材料中疑似包含 5 个 badcase，我已按“用户问题 / 模型回答 / 人工备注”拆分。
```

用户只需要确认拆分是否大体正确。

## 6. 标准数据对象

### Eval Evidence Case

所有输入最终统一成 `EvalEvidenceCase`。

```json
{
  "id": "case_001",
  "source": {
    "fileName": "demo_badcases.csv",
    "rowId": "12",
    "sourceType": "eval_result"
  },
  "content": {
    "query": "我快没油了，帮我找一个顺路的加油站，不要绕太远",
    "expected": "推荐顺路加油站，并说明绕行成本和到达方式",
    "actual": "为你推荐附近加油站"
  },
  "signals": {
    "passed": false,
    "score": 0.42,
    "errorType": "constraint_missing",
    "category": "车载助手"
  },
  "trace": {
    "traceId": "trace_001",
    "modelVersion": "demo-agent-v1",
    "agentName": "",
    "toolCalls": [],
    "handoffs": [],
    "retrievedContext": []
  },
  "readiness": {
    "level": "A",
    "missing": [],
    "limitations": []
  }
}
```

### Failure Pattern

参考 Deep Fix，失败模式不是业务 error_type，而是机制类型。

```json
{
  "caseId": "case_001",
  "isBadcase": true,
  "confidence": 0.88,
  "pattern": "Semantic",
  "subType": "multi-intent",
  "failureSignals": [
    "识别了加油需求",
    "遗漏了顺路约束",
    "遗漏了绕行成本说明"
  ],
  "mechanismGap": "模型没有把用户的复合约束转成评测点",
  "requiresHumanReview": false
}
```

### Problem Cluster

```json
{
  "clusterId": "cluster_constraint_001",
  "clusterName": "复合约束遗漏",
  "pattern": "Semantic",
  "subTypes": ["multi-intent", "implicit intent"],
  "caseCount": 12,
  "representativeCaseIds": ["case_001", "case_006"],
  "failurePattern": "模型能识别主意图，但遗漏用户附加约束、优先级或解释要求。",
  "repairDirection": "补充多约束、多目标、需要解释依据的训练与回归评测样本。"
}
```

### Repair Recipe

```json
{
  "recipeId": "repair_constraint_001",
  "clusterId": "cluster_constraint_001",
  "targetAbility": "复合约束理解与答案完整性",
  "assetMix": {
    "regression": 0.5,
    "training_candidate": 0.3,
    "negative": 0.1,
    "gold_candidate": 0.1
  },
  "generationRules": [
    "每条样本必须包含 expected_behavior",
    "每条样本必须包含 2-4 个 eval_points",
    "必须覆盖原始失败信号中的关键约束",
    "部分样本应构造成边界或反例"
  ]
}
```

## 7. Deep Fix 式问题发现方法

评测增强不应写成硬策略：

```text
如果 query 包含“不要绕太远”，就标记 constraint_missing
```

而应写成机制：

```text
证据 -> 失败信号 -> 失败模式 -> 问题族 -> 修复机制 -> 生成资产
```

### 7.1 失败模式分类

内置七类机制模式：

| 模式 | 判断问题 |
| --- | --- |
| Semantic | 模型是否误解、遗漏或拆错用户意图 |
| Context | 是否缺少历史、用户状态、环境状态或上下文被污染 |
| Retrieval / Knowledge | 正确信息是否没有被取到、取错、过期或冲突 |
| Routing / Orchestration | 工具、Agent、模式或 handoff 是否选错 |
| Parameter / Schema | 工具参数、槽位、单位、格式是否错误 |
| System Boundary | 是否把模型该做的事写成规则，或把代码该保证的事交给 prompt |
| Evaluation | 是否缺少回归、负例、边界样本或可测标准 |

这七类是“问题发现的坐标系”，不是最终业务标签。

### 7.2 聚类原则

聚类优先看失败机制，而不是业务表面相似度。

错误做法：

```text
所有“加油站”样本聚一组。
```

正确做法：

```text
所有“主意图正确但附加约束遗漏”的样本聚一组。
```

这允许跨业务域发现共性：

| 业务表面 | 失败机制 |
| --- | --- |
| 车载助手遗漏“顺路、绕行成本” | Semantic / multi-intent |
| 企业知识库遗漏“先看哪些指标、如何判断” | Semantic / multi-intent |
| 研发 Agent 遗漏“不要改接口，只改测试” | Semantic / multi-intent |

这就是评测增强的技术价值：从 case 进入 pattern，而不是停留在关键词或业务标签。

### 7.3 分析过程

```text
Step 1. 显性失败识别
  passed=false / score 低 / error_type 非空 / actual 缺失

Step 2. 隐性失败判断
  expected 与 actual 对比，提取遗漏、偏移、格式、风险、追问缺失等信号

Step 3. 失败模式分类
  将信号映射到 Deep Fix 七类机制模式

Step 4. 问题族聚类
  依据 failureSignals、pattern、subType、category、query 语义进行聚合

Step 5. 诊断卡生成
  输出失败模式、证据样本、可能根因、业务影响、修复方向

Step 6. 修复 recipe 生成
  将诊断转成批量生成参数和输出契约
```

### 7.4 模型与规则的边界

模型负责：

- 语义理解。
- 隐性 badcase 判断。
- 失败信号提取。
- 失败模式分类。
- 聚类命名。
- 根因假设。
- 修复策略。

代码 / 规则负责：

- 文件解析。
- 字段安全处理。
- readiness 计算。
- 显性失败识别。
- schema 校验。
- 导出格式。
- provenance 记录。

人工负责：

- 低置信度判断确认。
- 问题族合并 / 拆分 / 重命名。
- 根因假设采纳。
- gold candidate 确认。

## 8. 用户交互模型

### 8.1 交互原则

分析过程固定，交互点有限。

用户不是和系统无限聊天，而是在关键检查点做高价值确认。

```text
系统先给判断，用户做确认。
系统提供默认路径，用户只修正关键偏差。
系统保留修改结果，后续步骤局部更新。
```

### 8.2 五个检查点

#### 检查点 1：材料理解

系统展示：

- 我识别到的文件类型。
- 我抽取出的候选 case 数。
- 我推断的字段角色。
- 我认为缺失的证据。
- 这份材料当前能做的分析等级。

用户动作：

- 确认。
- 修正字段角色。
- 删除误抽取 case。

#### 检查点 2：Badcase 判断

系统展示：

- 显性失败。
- 隐性失败候选。
- 不确定样本。

用户动作：

- 接受高置信度判断。
- 只处理不确定样本。
- 批量排除误判。

#### 检查点 3：问题族

系统展示：

- cluster cards。
- 每组代表样本。
- 共性失败信号。
- pattern / subType。

用户动作：

- 合并。
- 拆分。
- 重命名。
- 标记“不成立”。

#### 检查点 4：诊断卡

系统展示：

- 问题族名称。
- 失败模式。
- 证据样本。
- 可能根因。
- 业务影响。
- 修复方向。

用户动作：

- 采纳。
- 修改。
- 降级为待复核。

#### 检查点 5：生成目标

系统展示推荐 asset mix。

用户动作：

- 选择生成回归评测数据。
- 选择生成训练候选数据。
- 选择生成负例 / 边界样本。
- 选择混合导出。

### 8.3 防止无限循环

产品约束：

- 每个阶段最多一次“重新分析全部”。
- 用户修改 cluster 后，只局部更新诊断和 recipe。
- 高置信度默认通过，低置信度进入复核。
- 每个检查点都有“接受推荐并继续”。
- 开放输入只用于修改名称、备注和修复方向，不作为主交互方式。

用户协作的目标不是把每个样本讨论到完美，而是：

```text
快速确认主要问题族是否成立。
```

## 9. UX 流程

### 总流程

```text
上传证据
-> 智能理解
-> 最小确认
-> Badcase 发现
-> 问题族地图
-> 诊断卡片
-> 修复策略
-> 批量生成
-> 复核导出
```

### 9.1 页面一：证据导入

目标：让用户无负担上传材料。

主文案：

```text
上传评测结果、badcase 表、用户反馈或测试备注。无需整理成固定模板，系统会先尝试理解其中的失败证据。
```

入口：

- 上传 CSV。
- 粘贴文本。
- 使用演示样例。

上传后反馈：

```text
我识别到这是一份车载助手 badcase 表，共 42 行。
已抽取 39 个候选 case，其中 21 个包含 expected 和 actual，可进入完整诊断。
```

### 9.2 页面二：材料理解确认

目标：让用户确认系统理解是否大方向正确。

界面结构：

- 左侧：原始字段 / 文本片段。
- 中间：系统抽取的 case。
- 右侧：字段角色和分析等级。

关键 UX：

- 不把字段名当作唯一依据。
- 每个字段角色显示解释。
- 缺失字段显示“影响”，而不是显示“错误”。

示例：

```text
缺少 score：不会影响 badcase 发现，但质量报告中无法统计原始评分分布。
缺少 expected：可以生成 silver expected candidate，需要人工确认后才能进入 gold/regression。
```

### 9.3 页面三：Badcase 发现

目标：将用户 loop 进失败发现，但只处理高价值不确定项。

界面结构：

- 顶部统计：显性失败、隐性失败、不确定、可忽略。
- 左侧过滤：pattern、置信度、category、modelVersion。
- 右侧 case 列表：query、expected、actual、failureSignals。

默认策略：

- 高置信度 badcase 自动选中。
- 低置信度进入 `needs_review`。
- 用户可以一键“接受全部高置信度”。

### 9.4 页面四：问题族地图

目标：把离散 badcase 变成可行动的问题族。

界面结构：

- Cluster 卡片网格。
- 每张卡显示：
  - 问题族名称。
  - 样本数量。
  - Deep Fix pattern。
  - 代表样本。
  - 失败信号。
  - 推荐修复方向。

用户动作：

- 合并相近问题族。
- 拆分混杂问题族。
- 重命名问题族。
- 标记为噪声。

交互重点：

```text
聚类不是让用户重新整理样本，而是让用户确认系统是否抓住了主要问题结构。
```

### 9.5 页面五：诊断卡片

目标：形成可讲解、可复核、可导出的诊断资产。

诊断卡内容：

- 问题族名称。
- 失败模式。
- 证据样本。
- 可能根因。
- 业务影响。
- 修复策略。
- 推荐输出资产。

文案约束：

- 使用“可能根因”“根因假设”“建议策略”。
- 不使用“真实根因已确定”。

### 9.6 页面六：修复策略

目标：从诊断自然转到数据生成。

系统根据 cluster 推荐 recipe：

- 同意图改写。
- 复合约束增强。
- 多轮追问构造。
- expected behavior 补全。
- eval points 补全。
- 负例 / 边界样本。
- 工具调用 / Agent 轨迹失败样本。

用户选择：

- 生成评测数据。
- 生成微调数据。
- 生成混合数据包。

### 9.7 页面七：批量生成

关键判断：

```text
技术上复用批量生成引擎，产品上不跳出评测增强流程。
```

用户不应该被带回普通 Quick Task 重新配置。

系统自动把诊断和 recipe 转成批量生成输入：

```text
代表 badcase
+ failureSignals
+ problem cluster
+ repairStrategy
+ assetIntent
+ output contract
```

生成页展示：

- 当前生成目标。
- 来源问题族。
- 输出类型比例。
- 生成进度。
- 保留率。
- 格式通过率。

### 9.8 页面八：复核与导出

结果按资产类型分 Tab：

- 回归评测样本。
- 训练候选样本。
- 负例 / 边界样本。
- rejected / needs_review。

导出：

```text
eval_cases.jsonl
train_alpaca.jsonl
negative_cases.jsonl
cluster_diagnosis.json
quality_report.json
provenance.json
```

P0 可先支持：

```text
eval_cases.jsonl
cluster_diagnosis.json
quality_report.json
```

## 10. 与现有 Quick Task 的关系

评测增强不替代 Quick Task。

三者关系：

```text
Quick Task：我有普通 seeds，要快速批量生成。
Fine-Tune Generation：我有高价值 seeds，要可控扩写。
Evaluation Enhancement：我有失败证据，要诊断问题族并生成修复数据。
```

底层可以复用：

- 文件解析能力。
- 字段识别能力。
- 批量生成能力。
- 导出能力。
- 安全拒识能力。

但用户体验上必须是独立工作流：

```text
评测增强先完成诊断和策略，再调用批量生成。
```

否则用户会感觉自己只是从一个上传页跳到了另一个上传页，产品心智不成立。

## 11. P0 范围

P0 必做：

- 新增评测增强入口。
- CSV 上传。
- 粘贴文本。
- 内置 badcase 样例。
- 智能材料理解。
- 字段角色推断。
- Readiness 等级。
- 显性 badcase 识别。
- 隐性 badcase 判断。
- Deep Fix 七类失败模式。
- 问题族聚类。
- 诊断卡片。
- 修复 recipe。
- 评测数据生成。
- 质量报告。
- 三件套导出。

P0 可简化：

- 聚类算法可以先用规则预分桶 + 模型命名。
- Agent trace 字段先作为可选字段展示，不做深度解析。
- XLSX / JSONL 可后置。
- 训练数据和负例混合导出可后置。

## 12. 成功指标

### 导入成功指标

- 用户上传非标准文件后，系统能抽取候选 case。
- 用户不需要手动改列名即可进入下一步。
- 字段缺失时系统能解释影响并给出可继续路径。

### 诊断成功指标

- 能把 badcase 聚成 3-8 个可解释问题族。
- 每个问题族有代表样本和失败信号。
- 低置信度样本进入人工复核，而不是污染主结果。

### 生成成功指标

- 每个 cluster 能生成结构化 eval case。
- 生成样本包含 expected behavior、eval points、asset intent 和 provenance。
- 导出文件能直接进入回归评测或人工标注流程。

### 复赛展示指标

- 从一份混乱 badcase 表开始。
- 2 分钟内看到系统理解和 readiness。
- 4 分钟内看到问题族地图。
- 6 分钟内看到诊断卡片和修复策略。
- 8 分钟内生成评测样本。
- 10 分钟内展示质量报告和导出资产。

## 13. 风险与约束

### 风险一：智能上传误解用户材料

控制：

- 展示系统理解结果。
- 保留原始证据引用。
- 所有推断带置信度。
- 低置信度进入确认。

### 风险二：模型诊断过度推断

控制：

- 使用“根因假设”。
- 诊断必须引用证据样本。
- 用户可降级或拒绝诊断。

### 风险三：交互陷入无限修改

控制：

- 固定检查点。
- 默认继续路径。
- 局部更新，不全量反复分析。
- 每阶段最多一次全量重分析。

### 风险四：产品滑向完整评测平台

控制：

- 不做 runner。
- 不做 judge 平台。
- 不做 CI gate。
- 只做 failure evidence 到 data asset 的转换。

## 14. 最终产品原则

```text
不要让用户整理数据来适应系统。
让系统先理解用户已有证据，再把不确定之处交给用户确认。
```

```text
不要把 badcase 修成规则堆。
把 badcase 抽象成失败模式，再把失败模式转成可复用修复机制。
```

```text
不要把评测增强做成聊天。
把用户放进有限检查点，让用户高效确认问题发现和聚类结果。
```

```text
不要让用户从评测增强跳回普通批量任务。
评测增强应在完成诊断和 recipe 后，内嵌调用批量生成能力。
```

最终形态：

```text
智能证据摄取
+ Deep Fix 问题族抽象
+ 有限人机确认
+ 批量生成引擎
+ 可追溯资产导出
```
