# CorpusFlow 两件专利红队报告

生成日期：2026-07-03

## 1. 红队原则

本报告不判断“检测器如何规避”，只判断提交文本中哪些段落容易被质检、代理人或检测工具认为：

1. 文风过像 AI 生成。
2. 技术事实不够落地。
3. 说明书口径与代码/实施状态不一致。
4. 权利要求或发明内容过度写死具体实现。
5. 技术效果没有绑定技术特征。

## 2. 案件一：失败证据数据资产生成方法及系统

文件：

`docs/superpowers/patents/disclosures/失败证据数据资产生成方法及系统/说明-失败证据数据资产生成方法及系统-20260528183806.md`

### 2.1 总体判断

该案主线成立，且比第二案更适合作为优先修订对象。风险不在“套话词过多”，而在于：

1. 部分机制与当前代码实现不完全一致。
2. 方法流程从 S1 到 S13 过齐，像由 AI 一次性展开的完整方案。
3. `qualityScore`、`clusterPurity`、`expectationConfidence`、`tool_argument_error`、`reviewStatus` 等词会触发“是否已实现/是否有证据”的追问。
4. 技术效果仍有部分“自动、提高、降低、闭环”式概括，需要绑定具体处理步骤。

### 2.2 高风险段落表

| 位置 | 风险类型 | 问题 | 蓝队处理 |
| --- | --- | --- | --- |
| B1 技术问题 | 文风风险 | “如何...”连续 5 条，结构整齐，像产品需求拆解 | 改成一段总问题 + 2-3 个工程约束，减少清单感 |
| S4 补全期望行为 | 实现口径风险 | 期望行为补全写得很强，容易被问是否已有 `expectationSource / expectationConfidence` | 改为“在一个实施例中可记录来源和置信状态”；强调补全失败进入复核 |
| S5 计算证据完整度 | 实现不一致 | `completenessScore`、`expectationConfidence` 不是当前代码完全一致字段 | 改为“完整度等级”，数值分作为可选实施例 |
| S6 提取失败信号 | 实现不一致 | `expectedFeatureSet`、`actualFeatureSet`、`tool_argument_error` 当前不是稳定实现事实 | 改为可选从属特征；主线保留“工具调用缺失/工具选择错误/约束遗漏”等已支撑信号 |
| S8 形成问题族 | 实现不一致 | `clusterPurity` 写成公式，但代码目前是 `quality.purity` 分级 | 改为“问题族一致性状态”，公式放可选实施方式 |
| S10 质量校验 | 实现不一致 | `qualityScore` 公式过完整，且字段名和代码不完全一致 | 改为质量状态/质量门；公式放从属或实施例 |
| S11 provenance | 实现口径风险 | `schema 版本、规则版本、复核状态` 可能不是全部已实现 | 改为“可包括”，并将未实现字段移入可选实施方式 |
| B3 技术效果 | 文风风险 | “降低/提高/便于”列表较直，部分效果未绑定步骤 | 每条改为“由于 Sx...因此...” |
| B4 创新点 | 结构风险 | 7 条完整创新点像摘要式枚举 | 合并为主创新组合 + 从属保护点，不要每条都像结论 |
| 实施例二/五 | 实现口径风险 | 示例 JSON 中 `qualityScore`、`reviewStatus` 易被认为已落地 | 保留为“示例输出字段”，或改成当前代码存在字段 |

### 2.3 事实一致性红线

依据：

`docs/superpowers/patents/disclosures/失败证据数据资产生成方法及系统/说明-待实现项-交底书对齐.md`

不能强写为已实现：

1. `expectedTool`
2. `expectationSource`
3. `expectationConfidence`
4. `tool_argument_error`
5. 独立 `review_tasks.jsonl`
6. 数值化 `qualityScore`
7. 数值化 `clusterPurity`
8. 数值化 `completenessScore`

可以强写为已有支撑：

1. 字段角色识别。
2. A-D 完整度分级。
3. 失败信号抽取。
4. 问题簇聚合。
5. cluster `accepted / rejected / pending`。
6. `training_candidates.jsonl` / `eval_cases.jsonl` / `negative_cases.jsonl` / `quality_report.json` / `provenance.json`。
7. 批次变体：`source_replay`、`colloquial_voice`、`constraint_rich`、`cross_domain_followup`、`negative_boundary`、`regression_probe`。

### 2.4 蓝队样章优先级

先改：

1. B1 技术问题。
2. B2.1 中 S4-S11。
3. B3 技术效果。
4. 实施例二、实施例五。

暂不先改：

1. 背景技术查新部分。
2. 附图说明。
3. 替代方案。

原因：打回风险主要集中在发明内容和实施例，不在形式性章节。

## 3. 案件二：语义骨架双路径可控扩写方法及系统

文件：

`docs/superpowers/patents/disclosures/语义骨架双路径可控扩写方法及系统/说明-一种基于语义自由度预算的语料裂变控制方法及系统-20260611113658.md`

### 3.1 总体判断

该案技术主线有价值，但当前文本更像“算法架构设计稿”。主要风险是：

1. 概念和公式密度过高。
2. 英文字段名、伪代码和对象结构连续出现。
3. “语义自由度账本、预算、投影、裂变轨迹、反馈回写”主线成立，但缺少足够自然的实施例穿插。
4. 如果公司质检人员按普通专利说明书标准看，可能认为公开内容过抽象或实现依据不足。

### 3.2 高风险段落表

| 位置 | 风险类型 | 问题 | 蓝队处理 |
| --- | --- | --- | --- |
| A2 现有技术 | 文风风险 | 查新摘要连续列举论文/专利，段落模式高度一致 | 保留核心对比，压缩为“几类现有方案”；详情移到查新附件 |
| B1 技术问题 | 结构风险 | 9 条“如何...”过整齐 | 改成 1 个总问题 + 3 个具体技术难点 |
| B2.1 方法流程 | 抽象风险 | S1-S20 完整链条太像算法 pipeline | 合并步骤，突出独权主链，细节放实施例 |
| 语义自由度分解模块 | 概念堆叠 | `semantic_freedom_unit` 定义长，字段/算子/不变量密集 | 先给 seed 示例，再解释字段 |
| 自由度容量计算 | 公式风险 | `freedom_capacity` 公式过早出现 | 改为“根据至少一项指标确定容量”，公式放可选实施例 |
| 语义自由度账本 | 设计稿风险 | JSON-like 对象字段过多 | 用中文说明主要字段；完整字段表放附录或实施例 |
| 预算分配模块 | 公式密集 | `raw_budget`、`pass_rate`、`risk_decay` 等连续公式 | 独权不写公式；说明书保留一个简化例子 |
| 预算可行性投影 | 数学味过强 | 约束表达接近论文/算法设计文档 | 改成代理人句式：“修正原始预算以满足...” |
| 语义守门与反馈回写 | 公式密集 | `next_budget`、`feedback_score` 公式多次重复 | 保留一处，删除重复公式，转成流程说明 |
| 关键技术参数表 | 检测风险 | 大量英文变量表格容易像 AI 生成技术文档 | 缩短表格，只保留主权利要求需要的 6-8 项 |
| B3 技术效果 | 文风风险 | 9 条效果过整齐，且标题加粗统一 | 合并为 4 条，每条绑定一个技术特征 |
| B4 建议优先保护 | 内部策略风险 | “建议...”像代理内部备忘，不适合正式交底正文 | 改为代理人沟通附件，不入正式正文 |

### 3.3 蓝队重构建议

第二案不要直接逐段改，而应先重构章节：

1. 主线压缩为 7 步：
   - 获取 seed 与目标。
   - 构建语义骨架。
   - 识别不变量和自由度。
   - 建立自由度账本。
   - 根据覆盖/风险/反馈确定预算。
   - 生成候选语料并记录轨迹。
   - 根据质量结果回写账本并调整下一轮分布。
2. 公式改为实施例，不要在发明内容主线堆公式。
3. 字段名保留中文解释，英文变量只作为示例字段。
4. 每个核心概念必须跟一个 seed：
   - “把空调调到 22 度”
   - “找附近的店，但不要便利店”
   - “不是的，在 QQ 音乐里播放”
5. 技术效果从 9 条压缩为 4 条：
   - 控制语义越界。
   - 降低近重复。
   - 保留生成轨迹。
   - 使质量反馈影响下一轮分布。

### 3.4 第二案是否先改

不建议先改第二案全文。

原因：

1. 第二案材料更抽象。
2. 公式和字段过多，重构成本高。
3. 第一案更贴近当前代码和产品，更容易先建立一套可复用蓝队模板。

建议在第一案样章通过后，再用同一套规则处理第二案。

## 4. 跨案件共性风险

### 4.1 AI 文风风险

高风险表现：

1. “本申请要解决以下具体问题”后连续 8-10 条问题。
2. 每条技术效果都以“提高/降低/增强/便于”开头。
3. 每个对象都被完整定义一次，缺少自然承接。
4. 公式、JSON、字段表、流程图说明连续出现。
5. 缺少“在一个实施例中”“可以”“例如”“不限定”等代理人缓冲。

### 4.2 专利质检风险

高风险表现：

1. 独权写具体公式。
2. 独权写具体文件名。
3. 独权写具体阈值。
4. 背景技术写出发明点。
5. 实施例只是重复发明内容。
6. 技术效果只写结果，不写由哪个技术特征导致。

### 4.3 工程事实风险

高风险表现：

1. 文本声称已有完整人工复核队列，但代码只有 cluster status。
2. 文本声称数值质量分，但代码是分级或嵌套置信度。
3. 文本声称某失败信号独立枚举，但代码只有相近枚举。
4. 文本声称自动补全期望行为，但当前更接近规则识别和候选推断。

## 5. 蓝队改写验收标准

每个修订段落必须满足：

1. 有明确输入。
2. 有明确处理动作。
3. 有明确输出或状态变化。
4. 有异常/降级路径。
5. 有事实来源或可实施说明。
6. 技术效果绑定上述处理动作。
7. 未实现内容使用“可选实施例/可以/在一个实施例中”处理。
8. 独权级内容不上具体数值、公式、文件名。
