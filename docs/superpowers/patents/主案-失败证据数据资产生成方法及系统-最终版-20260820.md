## B. 背景技术

### B1. 与本申请相关的现有技术背景情况

大语言模型应用在实际运行时会产生失败案例，这些失败案例通常散落在评测日志、用户反馈、人工标注表或运行trace中。现有做法通常是人工挑选部分失败案例加入评测集或负例库，但这种做法存在明显问题。

失败证据的字段来源多样、命名不一致，难以统一处理。同样是"用户输入"，可能记作query、user_message、instruction或prompt；同样是"实际输出"，可能记作output、response、actual或result。字段角色识别依赖人工对照，导致大量失败证据因字段名不匹配而被忽略。另一个普遍情况是失败证据中缺失关键信息，但缺失类型不同、可补全程度不同。部分证据缺期望行为，部分缺上下文，部分缺执行信息。现有方法通常直接丢弃不完整证据，或人工补全后再处理，导致数据利用率低、人工成本高。

此外，失败原因难以归类和追溯，同类问题重复出现。失败证据通常只记录"测试未通过"，但无法说明是工具未调用、工具选择错误、上下文缺失还是输出格式问题。无法按失败原因聚类管理，导致相同问题反复出现、修复策略分散。最后，不同失败原因适合生成不同类型的数据资产，但现有方法缺少分流机制。工具调用失败适合生成训练样本、输出格式错误适合生成负例、多轮对话失败适合生成回归评测用例，但现有方法通常只生成单一类型资产，无法按问题特征匹配资产用途。

### B3. 现有技术的缺陷和不足

现有可观测到的技术方案至少存在以下不足：

1.字段角色识别依赖人工对照。失败证据来源多样，字段命名不统一。现有方案通常按固定字段名读取数据，当字段名不匹配时需要人工建立映射关系。这种做法在处理大量异构数据源时效率低下，且容易因字段名变化导致数据丢失。

2.缺失信息处理方式单一。现有方案对不完整证据通常采取直接丢弃或要求人工补全两种极端做法。实际上，不同类型的缺失信息可补全程度不同：部分可从上下文推断，部分可从工具约束补全，部分可标记为需人工复核。现有方案缺少对缺失信息的分级处理机制。

3.失败原因难以系统化归类。失败证据通常只记录最终结果（通过或未通过），缺少对失败原因的结构化描述。现有方案即使人工标注失败原因，也难以保证标注粒度和分类体系的一致性，导致同类问题无法有效聚合，修复策略分散。

4.问题聚类缺少根因关联。即使对失败案例进行聚类，现有方案通常基于表面特征（如输入文本相似度）而非失败根因。这导致表面相似但根因不同的案例被错误聚合，或表面不同但根因相同的案例被分散处理。

5.资产用途与问题特征脱节。不同失败原因适合生成不同类型的数据资产。工具调用失败适合生成训练样本以改善模型工具使用能力，输出格式错误适合生成负例以约束输出格式，多轮对话失败适合生成回归评测用例。现有方案缺少根据失败信号和问题特征自动确定资产用途的机制。

6.来源信息和质量状态记录不完整。生成的数据资产通常缺少完整的来源记录，难以追溯到原始失败证据和生成策略。当资产在下游使用中出现问题时，无法快速定位来源并调整生成策略。现有方案也缺少对资产完整度和质量状态的结构化记录。

## C. 发明内容

### C1. 本申请所要解决的技术问题

本申请要解决的核心问题是：在大模型/Agent迭代过程中，基于已有的失败案例，从异构、不完整、失败原因多样的失败证据中，自动化生成可溯源的数据资产。

在实际应用中遇到的典型场景包括：某车载语音助手迭代过程中积累了300+的失败证据，一般会分散在评测人员的评测日志（字段名user_query/bot_response）、人工标注表（字段名prompt/answer/reviewer_comment）、运行trace（字段名input/output/tool_calls）当中。字段名不统一导致手工梳理效率低下、数据处理出错概率高。部分证据缺少期望行为，但可从人工备注"应调用XX工具"补全；失败原因只记录"测试未通过"，难以区分是工具路由错误、参数缺失还是上下文丢失。需要一种能够自动识别字段角色、尝试补全缺失信息、提取失败信号并按信号类型生成对应资产（训练候选/评测用例/负例）的方法。

具体是需要解决两个关键挑战：

首先，如何从字段名不统一、关键信息缺失的异构数据源中构建标准证据对象。失败证据可能来自评测日志、运行trace、人工标注表或用户反馈，字段名称和数量不固定。期望行为可能缺失，但缺失类型和可补全程度不同。需要一种能够识别字段实际角色、评估证据完整度、尝试从可用信息补全缺失部分并标记补全来源的机制。

其次，如何将失败原因从模糊的"测试未通过"转换为结构化的失败信号，并基于失败信号聚类形成问题族、确定资产用途。需要一种能够基于期望行为与实际输出的差异提取失败信号（如工具未调用、工具选择错误、上下文缺失）、根据失败信号和上下文进行聚类、按问题族特征确定资产应用于评测/训练/负例的机制，同时记录每个资产的来源追溯信息。

### C2. 本申请的技术方案

#### C2.1 方法流程

本申请提供一种失败证据数据资产生成方法，包括以下步骤：

**S1. 通过对数据字段的文本归一化实现获取失败证据原始数据**

总体设计是：先通过构建宽口的字段识别算法，能在类似于网页前后端实现从评测记录文件、运行日志、trace文件、人工标注表或用户反馈中，获取失败证据原始数据。每条原始数据包含多个字段，字段名称和数量不固定，但都可以被归一化，例如：query｜input｜文本｜user input等统一映射为”input输入”，解决数据格式不统一问题。

代码实现对应：`src/utils/evaluationMode.ts:336-398 parseEvidenceFile()` 读取jsonl/csv/json格式的失败证据文件，返回原始数据数组。

**S2. 具体到数据字段的角色识别**

具体来看：字段识别算法不仅要做到多文本归一处理能力，更需要对每条失败证据的字段进行角色识别，判断各字段实际承载的信息类型。字段角色包括但不限于：交互内容（用户输入、系统输出）、期望行为、实际输出、上下文信息、执行信息、评测判断、人工标注和元数据。

字段角色识别基于字段名、字段值内容特征和预设的角色别名映射表。当字段名匹配已知别名时，直接映射到对应角色；当字段名未知时，根据字段值的内容特征（如是否包含工具调用、是否为对话历史、是否为评分值等）推断角色。为每个字段分配角色标签和角色置信状态。

代码实现对应：`src/utils/evaluationMode.ts:265-334 identifyFieldRole()` 基于字段名和内容特征识别字段角色，返回角色类型（identity/input/actual/expected/context/tooling/judgment/runtime/annotation）和置信度。

**S3. 基于数据字段的准确抓取和归类，构建标准证据对象**

根据识别出失败证据中的的字段角色，自动将失败证据转换为标准证据对象。标准证据对象包含以下结构化字段：

- 交互内容：用户输入和系统输出的完整对话历史
- 实际输出：本次失败案例中系统的实际输出
- 期望行为：系统应该产生的期望输出
- 上下文信息：多轮对话的上下文、用户画像或业务场景信息
- 执行信息：工具调用记录、中间步骤、执行轨迹
- 评测判断：自动评测结果、评分、失败标记
- 人工标注：人工添加的备注、标签或修正信息
- 来源记录：原始数据来源、采集时间、数据版本

当原始数据中缺少期望行为时，系统可从人工标注备注中收集补充信息（如失败原因描述），合并到标注字段中，或标记为需人工确认。

评估证据完整度，根据关键字段的存在情况和质量状态，将证据完整度分为A（完整）、B（较完整）、C（部分缺失）、D（不可用）四个等级。完整度评估结果记录到标准证据对象中。

代码实现对应：
- 标准证据对象定义：`src/utils/evaluationMode.ts:47-75 EvalEvidenceCase`
- 字段角色定义：`src/utils/evaluationMode.ts:27-45 EvidenceFieldRole`
- 完整度评估：`src/utils/evaluationMode.ts:88-90 EvidenceCompleteness`

**S4. 通过对比期望行为与实际输出，提取失败信号**

基于期望行为与实际输出的差异，从标准证据对象中提取失败信号。失败信号是对失败原因的结构化描述，类型包括但不限于：

- 工具未调用：期望调用工具但实际未调用
- 工具选择错误：调用了错误的工具
- 工具参数缺失：工具调用缺少必要参数
- 工具参数错误：工具参数值不符合约束
- 上下文缺失：缺少必要的上下文信息导致输出错误
- 上下文忽略：存在上下文但未被正确使用
- 输出格式错误：输出内容不符合格式要求
- 输出幻觉：输出包含虚假或无依据的信息
- 多轮承接失败：多轮对话中未正确承接上文
- 指代消解失败：指代词或省略成分未正确解析
- 安全规则违反：输出违反安全或合规要求
- 执行超时：处理过程超出时间限制

每个失败信号包含信号类型、触发条件、相关证据字段引用和置信度。一条失败证据可能包含多个失败信号。

代码实现对应：`src/utils/evaluationMode.ts:92-105 FailureSignal`

**S5. 结合S4的产出，收敛形成问题族**

基于失败信号和上下文信息，将多条失败证据聚类形成问题族。问题族是具有共同失败模式和根因假设的失败证据集合。

问题族聚类考虑失败信号类型、信号组合模式、上下文特征相似度和业务场景相关性。每个问题族包含：

- 代表性案例：该问题族的典型失败证据
- 根因假设：对该问题族共同根因的推测
- 修复策略：针对该根因的建议修复方向
- 案例列表：属于该问题族的所有失败证据索引
- 质量状态：该问题族的确认状态和优先级

代码实现对应：

**S6. 根据问题族特征，决定生成哪类数据资产**

根据问题族特征和失败信号类型，确定数据资产的用途规划。不同失败原因适合生成不同类型的资产：

- 训练候选：适合用于模型训练以改善特定能力（如工具调用类失败）
- 回归评测：适合加入评测集以防止功能退化（如多轮对话类失败）
- 负例样本：适合作为负例约束模型行为（如输出格式类失败）
- 人工复核：需要人工确认或修正的案例（如低置信度或高风险案例）

在一种实施方式中，系统可基于预设规则自动判定：工具调用类失败优先生成训练候选，输出格式类失败优先生成负例样本，多轮对话类失败优先生成回归评测用例，低置信度或高风险案例标记为人工复核。

按用途规划，将标准证据对象转换为对应格式的数据资产。在转换过程中，系统同步写入来源记录，确保每条资产都可追溯：

- 原始证据标识：追溯到具体的原始失败证据
- 所属问题族：该资产来自哪个问题族
- 生成策略：采用的资产生成规则和转换逻辑
- 生成时间：资产生成的时间戳
- 质量状态：资产的完整度等级和确认状态

**S7. 按质量分级导出资产**

根据数据资产的完整度、质量确认状态和用途类型，将资产分为至少两类进行差异化导出，避免低质量资产直接进入下游系统：

- 正式资产：完整度高且质量已确认的资产，可直接用于评测或训练

- 复核任务：完整度低、存在冲突或高风险的资产，标记为需要人工复核

导出时完整保留来源记录和质量状态信息，便于下游使用时判断可信度，出现问题时快速追溯来源。

#### C2.2 系统实施方式

本申请还提供一种失败证据数据资产生成系统，对应上述方法流程S1-S7，包括：

- 数据获取模块：从评测日志、trace文件、人工标注表等多种来源获取失败证据原始数据
- 字段角色识别模块：通过字段名匹配和内容特征推断，识别每个字段的角色和置信度
- 证据标准化模块：将异构数据转换为标准证据对象，并评估完整度
- 失败信号提取模块：对比期望行为与实际输出，提取结构化的失败信号
- 问题聚类模块：基于失败信号和上下文特征，将失败证据聚类形成问题族
- 资产生成模块：按问题族特征生成不同用途的数据资产
- 来源追溯模块：为每条资产记录原始证据、问题族、生成策略等来源信息

各模块通过数据流管道连接，原始失败证据经过字段识别、标准化、信号提取、问题聚类后，最终输出包含评测用例、训练候选、负例及完整来源记录的资产包。

### C3. 本申请与现有技术的主要区别

**区别一：处理异构数据源的能力不同**

现有方案按固定字段名读取数据（如只认"query"字段作为用户输入），当数据源字段名不匹配时需要人工建立映射关系。本申请通过字段角色识别机制，基于字段名、内容特征和预设别名映射，自动识别字段实际角色。同样是用户输入，无论记作query、user_message、instruction还是prompt，都能识别为"交互内容-用户输入"。这避免了因字段名不匹配导致的数据丢失，提高了对异构数据源的处理覆盖率。

**区别二：失败原因的结构化处理方式不同**

现有方案中失败证据通常只记录"测试未通过"或简单的文本描述，难以系统化归类。本申请通过失败信号提取机制，基于期望行为与实际输出的具体差异，将失败原因转换为结构化的失败信号（如工具未调用、工具选择错误、上下文缺失、输出格式错误等）。基于失败信号进行问题族聚类，使具有共同根因的失败案例聚合在一起，便于统一分析和修复。

**区别三：资产用途与失败特征的匹配机制不同**

现有方案通常将失败案例生成单一类型的资产（如都加入评测集），未根据失败原因区分资产用途。本申请根据失败信号类型和问题族特征，自动确定资产应用于训练、评测、负例还是人工复核。工具调用类失败生成训练候选以改善模型工具使用能力，输出格式类失败生成负例以约束输出格式，多轮对话类失败生成回归评测用例。同时为每个资产记录完整的来源信息，包括原始证据标识、所属问题族、生成策略、质量状态，使资产在下游使用中出现问题时能够快速追溯来源。

### C4. 本申请的技术效果

**效果一：提高了失败证据的处理覆盖率和利用率**

具体到数据字段的角色识别 — 字段角色识别机制（S2）使系统能够处理来自不同数据源、字段命名不一致的失败证据。基于数据字段的准确抓取和归类，构建标准证据对象 - 证据完整度评估（S3）使系统能够利用部分缺失但可用的失败证据，而非简单丢弃。相比现有方案按固定字段名读取导致的数据丢失和直接丢弃不完整证据的做法，本申请从更多异构数据源中提取有效信息，降低了人工补全成本。

**效果二：使失败原因可系统化归类和追溯**

通过对比期望行为与实际输出，提取失败信号 - 失败信号提取（S4）将失败原因从模糊描述（"测试未通过"）转换为结构化的失败信号（工具未调用、工具选择错误等），使失败原因可系统化归类和统计分析。结合S4的产出，收敛形成问题族 - 问题族聚类（S5）使同根因的失败案例聚合在一起统一处理，相比现有方案基于表面特征聚类导致的根因混杂问题，本申请的聚类结果更符合实际修复需求。

**效果三：提高了生成资产的针对性和可追溯性**

根据问题族特征，决定生成哪类数据资产 - 资产用途匹配机制（S6）使不同失败原因生成不同类型资产，相比现有方案生成单一类型资产的做法，提高了资产的可用性。来源记录机制使每个资产可追溯到原始失败证据、所属问题族和生成策略，当资产在下游使用中出现问题时，能够快速定位来源并调整生成策略。按质量分级导出资产 - 质量分级导出（S7）避免了低质量资产直接进入下游系统，降低了对下游系统的影响。

### C5. 本申请的技术创新点

**创新点一：异构失败证据的字段角色识别与标准化**

提出了基于字段名、内容特征和别名映射的字段角色识别机制。通过预设别名映射表（如query/input/user_message都映射为"用户输入"）和内容特征推断（如字段值包含工具调用则识别为"执行信息"），使系统能够处理字段命名不一致的异构失败证据。建立了证据完整度分级评估体系，根据关键字段的存在情况和质量状态将证据分为A（完整）、B（较完整）、C（部分缺失）、D（不可用）四个等级。当原始数据缺少期望行为等关键信息时，系统从人工标注备注中收集补充信息（如失败原因描述、修复建议等），合并到标注字段中，作为后续分析的辅助依据。这解决了现有方案按固定字段名读取导致的数据丢失问题，提高了对异构数据源的处理覆盖率。

**创新点二：失败信号提取与问题族聚类机制**

提出了基于期望行为与实际输出差异的失败信号提取机制，将失败原因从模糊的"测试未通过"转换为结构化的失败信号（如工具未调用、工具选择错误、上下文缺失、输出格式错误等）。每个失败信号包含信号类型、触发条件、相关证据字段引用和置信度。进一步提出了基于失败信号和上下文信息的问题族聚类机制，与现有方案基于表面特征（如输入文本相似度）聚类不同，本申请根据失败信号类型、信号组合模式、上下文特征相似度和业务场景相关性进行聚类，使具有共同失败模式和根因假设的失败证据聚合在一起，每个问题族包含代表性案例、根因假设和修复策略。

**创新点三：资产用途与失败特征的自动匹配机制**

建立了资产用途与失败特征的自动匹配机制。根据失败信号类型和问题族特征，自动确定资产应用于训练、评测、负例还是人工复核。在一种实施方式中，工具调用类失败优先生成训练候选，输出格式类失败优先生成负例样本，多轮对话类失败优先生成回归评测用例，低置信度或高风险案例标记为人工复核。这避免了现有方案将所有失败案例生成单一类型资产的问题，提高了资产的针对性和可用性。

**创新点四：完整的来源追溯体系**

设计了完整的来源记录结构，每个数据资产可追溯到原始失败证据标识、所属问题族、生成策略、生成时间和质量状态。在一种实施方式中，建立了基于质量条件的分级导出机制，将资产分为正式资产（高完整度且质量已确认）、候选资产（完整度中等或质量待确认）和复核任务（完整度低或高风险），使资产在下游使用中出现问题时能够快速定位来源并调整策略。这解决了现有方案生成资产缺少来源信息、质量问题难以追溯的问题。

### 实施例一：车载语音助手工具路由错误的处理

本实施例展示如何处理来自真实车载系统的工具路由失败证据，说明从原始数据到生成可用资产的完整流程。

**背景：** 某车载语音助手在迁移过程中积累了大量失败案例，这些案例记录在评测日志中，字段命名与内部开发trace记录、人工标注表都不一致。本实施例展示如何从这些异构数据中自动提取有价值的训练数据。

**E1.1 获取失败证据原始数据（对应方法S1）**

从车载系统迁移评测记录文件`migration_badcase_full.jsonl`中读取一条失败证据（已脱敏）：

```json
{
  "case_id": "migration-domain-error-0001",
  "user_input": "自动大灯怎么打开",
  "actual_output": "已为您打开自动大灯",
  "expected_behavior": "应落到正确车载技能域/工具 target_agent=Security Agent，不要落到 actual_agent=Command Agent",
  "failure_note": "落域错误 / wrong tool / 路由错误",
  "tool_calls": "[\"chat\"]",
  "grading_result": "fail",
  "tags": "wrong_tool;domain_error;migration_package"
}
```

**E1.2 字段角色识别（对应方法S2）**

系统扫描这条失败证据的每个字段，判断它们各自承载什么信息。关键问题是：不同数据源对同样的信息用不同的字段名，比如用户输入可能叫user_input、query、prompt或instruction，系统需要识别出它们都是"用户输入"这个角色。

系统对每个字段进行角色识别：

| 字段名 | 识别角色 | 依据 |
|--------|----------|------|
| case_id | 用例标识 | 字段名匹配"id"模式 |
| user_input | 交互内容-用户输入 | 字段名匹配"input/query"别名 |
| actual_output | 实际输出 | 字段名匹配"output/response"别名 |
| expected_behavior | 期望行为 | 字段名匹配"expected"别名 |
| tool_calls | 执行信息 | 字段值为JSON数组，内容为工具名 |
| grading_result | 评测判断 | 字段名匹配"result/judgment"别名 |
| failure_note | 人工标注 | 字段名匹配"note/comment"别名 |
| tags | 元数据 | 字段名匹配"tags/labels"别名 |

字段角色识别结果置信度均为高（0.9+），因为字段名和内容特征均匹配预设规则。

**E1.3 构建标准证据对象（对应方法S3）**

基于识别出的字段角色，系统将原始数据转换为标准格式。关键是把散乱的字段整理成结构清晰的对象，便于后续分析：

```typescript
{
  evidenceId: "migration-domain-error-0001",
  interaction: {
    userInput: "自动大灯怎么打开"
  },
  actualOutput: "已为您打开自动大灯",
  execution: {
    toolCalls: ["chat"]
  },
  evaluation: {
    result: "FAIL",
    evaluator: "auto"
  },
  annotation: {
    humanNote: "落域错误 / wrong tool / 路由错误",
    expectedBehavior: "应落到正确车载技能域/工具 target_agent=Security Agent，不要落到 actual_agent=Command Agent"
  },
  provenance: {
    sourceFile: "migration_badcase_full.jsonl",
    sourceId: "migration-domain-error-0001"
  },
  completeness: "A"
}
```

关键设计点：系统不创建独立的期望行为字段，而是从原始数据的`expected_behavior`字段和`failure_note`字段中收集信息，合并到`annotation`部分。这样保持了与代码实现的一致性：代码中标准证据对象的基础结构只包含interaction、actualOutput、execution、evaluation、annotation、provenance等字段，期望行为等补充信息作为注解的一部分保存。

系统评估证据完整度：用户输入、实际输出、执行信息、评测判断、人工标注五个关键字段均存在，评定为"A"（完整）。

**E1.4 提取失败信号（对应方法S4）**

系统从标注字段中提取期望行为信息："应落到正确车载技能域/工具 target_agent=Security Agent"，与实际执行情况（调用了"chat"工具，对应Command Agent）对比，发现不一致。这就是失败的根本原因：工具选择错误。

系统提取的失败信号：

```typescript
failureSignals: [{
  signalType: "wrong_tool",
  description: "期望调用Security Agent工具但实际调用了Command Agent",
  evidence: {
    userIntent: "车载技能查询",
    expected: "Security Agent",
    actual: "Command Agent"
  },
  confidence: 0.95
}]
```

这个失败信号清晰地说明了问题：不是输出内容不对（"已为您打开自动大灯"在语义上是正确的回复），而是工具路由选择错了（应该调用车载技能域的Security Agent，却调用了通用对话的Command Agent）。

**E1.5 形成问题族（对应方法S5）**

系统扫描所有失败证据，发现另外2条类似案例：

- migration-domain-error-0002："开空调"（期望Climate Agent，实际Command Agent）
- migration-domain-error-0003："导航去机场"（期望Navigation Agent，实际Command Agent）

这3条案例的共同特征：
- 都是车载技能查询意图
- 都期望调用特定车载技能域工具（Security/Climate/Navigation Agent）
- 都实际调用了通用对话工具（Command Agent）
- 失败信号都是"wrong_tool"

系统将它们聚类形成问题族：

```typescript
{
  clusterId: "CLUSTER_VEHICLE_ROUTING",
  clusterName: "车载技能工具路由错误",
  representativeCase: "migration-domain-error-0001",
  failureSignals: ["wrong_tool"],
  rootCauseHypothesis: "车载技能意图识别或工具路由策略存在缺陷",
  repairStrategy: {
    assetType: "training_candidates",
    reasoning: "工具调用类失败，适合生成训练样本改善工具路由能力"
  },
  caseCount: 3,
  quality: { confidence: 0.92, consistency: "high" }
}
```

问题族的价值在于：将表面不同（自动大灯、空调、导航三个不同功能）但根因相同（都是工具路由错误）的失败案例聚合在一起，便于统一分析和修复。

**E1.6 生成数据资产（对应方法S6-S7）**

根据问题族的特征（工具路由错误），系统判定应该生成训练候选资产，用于训练模型改善工具选择能力。生成的资产格式：

```jsonl
{"id":"ASSET_VEH_001","clusterId":"CLUSTER_VEHICLE_ROUTING","sourceCaseId":"migration-domain-error-0001","instruction":"自动大灯怎么打开","correct":"Security Agent","actual":"Command Agent","tags":["wrong_tool","domain_error"],"provenance":{"sourceFile":"migration_badcase_full.jsonl","sourceCaseId":"migration-domain-error-0001","problemCluster":"CLUSTER_VEHICLE_ROUTING","rootCauseHypothesis":"车载技能意图识别或工具路由策略存在缺陷"}}
```

关键点：生成的资产不仅包含训练数据本身（instruction、correct、actual），还包含完整的来源追溯信息（sourceFile、sourceCaseId、problemCluster、rootCauseHypothesis）。如果后续训练时发现这条数据有问题，可以立即追溯到原始失败证据，检查是生成策略有问题还是原始数据有问题。

这条资产的完整度评定为"A"，质量状态为"已确认"，因此导出为**正式资产**，可直接用于训练。

这条资产因为完整度高且来自明确的问题族，被分类为"正式资产"，可以直接用于模型训练。

### 实施例二：缺失字段的证据补全与降级处理

本实施例展示如何处理字段缺失的失败证据，说明证据完整度评估和补全机制。

**背景：** 并非所有失败证据都完整。实际场景中，部分证据缺少期望行为字段，但可以从其他字段推断或标记为需人工复核。本实施例展示如何处理这类不完整证据。

**E2.1 获取失败证据**

从人工标注表读取一条缺少期望行为的失败证据：

```csv
case_id,user_input,actual_output,reviewer_comment,status
R_156,"帮我设置明天早上7点的闹钟","好的，已经帮您设置好闹钟了。","没有调用工具，只是回复文本",rejected
```

**E2.2 字段角色识别**

系统识别字段角色：

| 字段名 | 识别角色 | 依据 |
|--------|----------|------|
| case_id | 用例标识 | 字段名匹配"id"模式 |
| user_input | 交互内容-用户输入 | 字段名匹配"input"别名 |
| actual_output | 实际输出 | 字段名匹配"output"别名 |
| reviewer_comment | 人工标注 | 字段名匹配"comment"别名 |
| status | 评测判断 | 字段名匹配"status"别名 |

关键发现：**缺少expected_behavior字段**，无法直接知道期望行为是什么。

**E2.3 构建标准证据对象并补全期望行为**

系统从人工标注"没有调用工具"推断期望行为：用户要求"设置闹钟"，应该调用工具设置闹钟，但实际只输出了文本。

```typescript
{
  evidenceId: "R_156",
  interaction: {
    userInput: "帮我设置明天早上7点的闹钟"
  },
  actualOutput: "好的，已经帮您设置好闹钟了。",
  expectation: {
    expectedOutput: "应调用工具设置闹钟，而不是仅回复文本"
  },
  execution: {
    toolCalls: []  // 未调用任何工具
  },
  annotation: {
    failureNote: "没有调用工具，只是回复文本\nexpectedtool=时间管理工具"
  },
  provenance: {
    sourceFile: "manual_review_0523.csv",
    sourceId: "R_156"
  },
  completeness: "B"  // 中等完整度：有输入、实际输出和人工标注，但缺少明确的期望输出
}
```

关键点：系统从人工标注字段（`reviewer_comment` 和可能存在的补充字段如 `expectedtool`）收集补充信息，合并到 `annotation.failureNote` 中。虽然原始数据缺少 `expected_behavior` 字段，但人工标注提供了失败原因，使证据仍可使用。完整度评定为"B"（有输入、实际输出和标注信息）。

**E2.4 提取失败信号**

```typescript
failureSignals: [{
  signalType: "tool_not_called",
  description: "期望调用工具但实际未调用任何工具",
  evidence: {
    userIntent: "设置闹钟",
    actualToolCalls: []
  }
}]
```

**E2.5 形成问题族并分配用途**

系统发现另外3条类似案例（工具应该调用但未调用），聚类为"工具未调用"问题族。这些案例都有人工标注说明失败原因，但原始数据中缺少明确的 `expected_behavior` 字段。

- 完整度：B（有输入、实际输出和人工标注）
- 资产分类：**候选资产**（因原始数据缺少明确的期望行为字段，需要人工复核确认）

**E2.6 生成候选资产**

```jsonl
{"id":"ASSET_CAND_001","clusterId":"CLUSTER_TOOL_NOT_CALLED","sourceCaseId":"R_156","instruction":"帮我设置明天早上7点的闹钟","actualOutput":"好的，已经帮您设置好闹钟了。","expectedBehavior":"应调用工具设置闹钟","failureNote":"没有调用工具，只是回复文本","tags":["tool_not_called"],"qualityStatus":{"completeness":"B","needsReview":true},"provenance":{"sourceFile":"manual_review_0523.csv","missingFields":["expected_behavior"]}}
```

关键点：这条资产被标记为"候选资产"，因为原始数据缺少明确的 `expected_behavior` 字段，期望行为是从人工标注的失败原因提取的。下游使用时需要人工复核确认期望行为是否准确理解，确认后才能用于训练。这避免了因理解偏差导致的训练数据质量问题。

### 实施例三：输出格式错误的负例生成

本实施例展示如何处理不同类型的失败（非工具路由错误），以及如何根据失败类型生成不同用途的资产。

**背景：** 某大模型应用要求输出JSON格式，但实际输出了自然语言。这类失败不适合生成训练候选（因为不是模型能力不足），而适合生成负例样本（用于约束模型输出格式）。

**E3.1 获取失败证据**

从人工标注表获取一条失败证据：

```csv
row_id,prompt,response,status,reviewer_comment
R_302,"返回JSON格式的用户信息","用户姓名是张三,年龄25岁。",rejected,"输出非JSON,不符合格式要求"
```

**E3.2 字段角色识别与构建标准证据对象**

这次的数据来源是CSV格式的人工标注表，字段命名与实施例一、二完全不同（prompt/response vs user_input/actual_output）。系统通过字段角色识别机制，识别出：

- row_id → 用例标识
- prompt → 交互内容-用户输入
- response → 实际输出
- status → 评测判断（rejected表示失败）
- reviewer_comment → 人工标注

构建标准证据对象时，系统发现缺少明确的期望行为字段。但人工标注中写了"输出非JSON,不符合格式要求"，系统从这句话推断出期望行为是"应输出JSON格式"，来源标记为"inferred_from_annotation"（从标注推断），置信度为"medium"（中等，因为是推断的而不是明确的）。

完整度评定为"MEDIUM"（缺少明确的期望输出示例，但可以使用）。

**E3.3 提取失败信号**

系统识别出这是输出格式错误，而非工具路由错误：

```typescript
failureSignals: [{
  signalType: "wrong_output_format",
  description: "期望JSON格式但输出自然语言",
  evidence: {
    expectedFormat: "JSON",
    actualFormat: "natural_language"
  }
}]
```

**E3.4 形成问题族并生成负例**

系统发现6条类似的格式错误案例，都是"要求JSON但输出了自然语言"，聚类为"JSON格式输出失败"问题族。

关键决策：系统判定这类失败应该生成负例样本，而非训练候选。原因是输出格式错误通常不是模型能力不足，而是需要约束模型行为。负例样本可以用于对比学习（告诉模型这样输出是错的）或安全过滤系统（拦截格式错误的输出）。

生成的负例资产：

```json
{
  "id": "ASSET_NEG_001",
  "clusterId": "CLUSTER_FORMAT_JSON",
  "sourceCaseId": "R_302",
  "instruction": "返回JSON格式的用户信息",
  "negativeOutput": "用户姓名是张三,年龄25岁。",
  "correctOutput": "{\"name\":\"张三\",\"age\":25}",
  "tags": ["wrong_output_format"],
  "provenance": {
    "sourceFile": "manual_review_0523.csv",
    "problemCluster": "CLUSTER_FORMAT_JSON"
  }
}
```

负例资产同时保留了错误输出（negativeOutput）和正确输出（correctOutput），便于下游系统进行对比学习。

## F. 权利要求建议

### 独立权利要求（方法）

一种失败证据数据资产生成方法，其特征在于，包括以下步骤：

获取失败证据原始数据，所述原始数据包含多个字段，字段名称和数量不固定；

对每条失败证据的字段进行角色识别，判断各字段实际承载的信息类型；

根据识别出的字段角色，将失败证据转换为标准证据对象，所述标准证据对象包含交互内容、实际输出、期望行为、上下文信息、执行信息、评测判断、人工标注和来源记录；

基于所述期望行为与实际输出的差异，从所述标准证据对象中提取失败信号；

基于所述失败信号和上下文信息，将多条失败证据聚类形成问题族；

根据所述问题族特征和失败信号类型，确定数据资产的用途规划，并按用途生成数据资产，同时写入来源记录；

根据所述数据资产的完整度和质量状态，将资产分类导出。
