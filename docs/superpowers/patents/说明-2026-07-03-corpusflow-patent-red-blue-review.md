生成日期：2026-07-03  
用途：内部返工前审查基线，供发明人、专利同事和代理人沟通使用。

## 0. 结论先行

两件专利被退回，不能只按“AI 生成检测分过高”理解。AI 检测分可能是触发器，但专利法视角下的核心风险是：

1. 技术方案是否由发明人真实确定，而不是由 AI 直接推演。
2. 说明书是否达到“清楚、完整，以本领域技术人员能够实现”为准。
3. 权利要求的上位概括是否能被说明书实施例支撑。
4. 一件案子是否聚焦一个总的发明构思。
5. 首稿是否已经写入足够技术细节，避免后续修改触发超范围风险。
6. 附图是否体现逻辑架构和内部处理关系，而不是只画“输入-处理-输出”的成功流程。

因此，返工目标不应是“洗 AI 生成嫌疑”，而应是“重建发明人事实链、技术方案链、实施例支撑链和代理人可撰写链”。检测器只作为最后的文本风险信号，不作为优化目标。

## 2. 法条审查框架

本工作稿按以下法条风险组织，不只按 AI 检测视角组织。

| 审查轴 | 法条锚点 | 本项目中的具体含义 |
| --- | --- | --- |
| 充分公开 | 专利法第26条第3款 | 说明书要写到本领域技术人员能实现。AI/算法类方案不能只写功能结果，必须写输入、数据对象、处理规则、判断条件、输出、异常/降级路径。 |
| 权利要求支持 | 专利法第26条第4款 | 独权中的上位概括必须能在说明书中找到足够实施例支撑。不能只在权利要求里写“质量分”“预算投影”“反馈回写”，说明书却没有足够数据结构和处理过程。 |
| 单一性 | 专利法第31条；实施细则关于总的发明构思 | 一件案子应围绕一个总发明构思。失败证据资产化、语义自由度扩写、污染防控、AI 检测规避不能混成一个案子。 |
| 超范围修改 | 专利法第33条 | 如果首稿没有写入关键数据结构、关键步骤、关键实施例，后续代理人难以补救。返工时要优先补足核心技术细节。 |
| 说明书结构 | 实施细则第20条 | 背景技术、发明内容、附图说明、具体实施方式要结构清楚；背景不能写入自己的发明点。 |
| 权利要求清楚/简要 | 实施细则第22条、第23条 | 术语统一，必要技术特征完整，独权不要用过细参数缩窄，也不要用纯功能性语言。 |

官方依据：

- 专利法第26条、第31条、第33条：https://www.cnipa.gov.cn/art/2020/11/23/art_97_155167.html
- 专利法实施细则第20条、第22条、第23条、第39条：https://www.cnipa.gov.cn/art/2023/12/21/art_98_189197.html

## 3. 参考案学习：代理人实际做了什么

### 3.1 文本差异概览

参考案不是简单“去 AI 味”。代理人一稿做了三件更关键的事：

1. 把发明点从具体实现参数上位到可保护的技术特征。
2. 把技术交底书中的研发说明转成“权利要求可承载的步骤链”。
3. 把具体参数、模型、阈值保留到实施例中，用于支撑而不是限制独权。

统计观察：

| 文件 | 中文字符数 | 特征 |
| --- | ---: | --- |
| 同事技术交底书 | 约 6766 | 技术细节密，模型/权重/传感器参数较多，像研发说明。 |
| 代理人一稿 | 约 17155 | 大量使用“一种可能的实现方式”“示例性的”“需要说明的是”，形成专利说明书口径。 |
| 质检表 | 约 712 | 主要扣分点不是 AI 文风，而是权利要求上位概括和形式问题。 |

### 3.2 参考案的核心上位动作

原交底书把方案写成：

- 语音传感器、手势摄像头、眼动追踪仪、环境传感器；
- MFCC、MediaPipe、MobileNetV3、Transformer；
- 高速驾驶时语音权重 0.7、手势 0.2、眼动 0.1；
- 具体模型参数、推理耗时、训练数据量。

代理人一稿将其上位为：

- 多模态交互数据；
- 车辆行驶数据；
- 当前行驶场景；
- 各交互模态的初步响应程度；
- 用户历史交互数据；
- 每种交互模态在此次交互中的信息贡献量；
- 对初步响应程度进行动态调整得到目标响应程度；
- 根据目标响应程度和多模态交互数据确定控制指令。

这对 CorpusFlow 的启发是：不要把独权写成具体字段名、文件名、模型名、公式名，而要找到可保护的中间概念。

主案可对应上位为：

- 失败证据；
- 字段角色；
- 标准证据对象；
- 期望行为；
- 失败信号；
- 问题族；
- 资产用途规划；
- 数据资产包；
- 来源记录。

第二案可对应上位为：

- 种子语料；
- 语义骨架；
- 语义不变量；
- 可变化语义资源；
- 语义自由度账本；
- 原始预算；
- 可执行预算；
- 样本级裂变计划；
- 裂变轨迹；
- 反馈回写后的下一轮裂变分布。

### 3.3 参考案质检表的真正信号

质检表扣分点包括：

- 权利要求 1 中直接记载了具体权重信息，建议上位为响应程度或者初步响应程度。
- 权利要求 1 中直接记载了具体目标权重，建议上位为响应程度或者初步响应程度。
- 说明书形式问题。

这说明内部质检看重的是：

1. 独权不要被具体参数限制。
2. 独权要抓抽象但可支撑的技术特征。
3. 说明书要为上位概括提供实施例。

对 CorpusFlow 的反推：

- 主案独权不应直接写死 `training_candidates.jsonl`、`eval_cases.jsonl`、`qualityScore`、`tool_argument_error` 等具体实现。
- 第二案独权不应直接写死阻尼公式、`exploration_floor`、`delta_max`、`fission_trace` 字段全集。
- 这些可以在实施例或从属权利要求中出现，用于支撑和回旋。

#### 主案独权主链建议

建议独权聚焦以下连续技术链，不把从属细节塞入独权：

1. 获取来自评测记录、日志、trace、badcase 表或用户反馈的失败证据。
2. 对失败证据中的字段进行角色识别，得到字段角色和角色置信状态。
3. 基于字段角色构建标准证据对象，标准证据对象包括交互内容、实际输出、期望行为或候选期望行为、上下文、执行信息、评测判断、人工备注和来源信息中的多项。
4. 基于实际输出与期望行为或候选期望行为的差异，提取失败信号。
5. 基于失败信号及上下文信息形成问题族。
6. 根据问题族生成资产用途规划，资产用途包括训练候选、回归评测、负例或人工复核中的至少两类。
7. 按资产用途规划生成数据资产，并为数据资产写入来源记录。
8. 基于质量条件将数据资产导出为正式资产、候选资产或复核任务。

独权中建议避免：

- 直接写 `tool_argument_error`；
- 直接写 `qualityScore` 公式；
- 直接写 `review_tasks.jsonl`；
- 直接写具体文件名；
- 直接写某个具体 LLM 或某个具体 schema；
- 直接写所有失败信号枚举。

这些应进入从权或实施例。

#### 第二案独权主链建议

建议独权收敛为：

1. 获取种子语料和目标生产约束。
2. 从种子语料构建语义骨架，并识别不得变化的语义不变量。
3. 从语义骨架中识别可变化语义资源，并构建语义自由度账本。
4. 根据覆盖目标、自由度容量、历史质量状态和约束关系，为语义自由度分配原始预算。
5. 根据自由度之间的耦合、互斥或条件关系，将原始预算转换为可执行预算。
6. 基于可执行预算生成样本级裂变计划，调度对应裂变算子生成候选语料，并记录裂变轨迹。
7. 根据候选语料的守门结果、重复结果或人工反馈，将质量结果归因回语义自由度账本。
8. 根据回写后的账本状态调整下一轮预算或裂变分布。

独权中建议避免：

- 不直接写完整公式；
- 不直接写所有自由度类型；
- 不把实体池/在线检索写成核心；
- 不写具体模型；
- 不写“AI 扩写”“大模型生成”作为核心；
- 不写“温度调高”“prompt 多样性”之类普通生成控制。

#### 第二案必须补强的实施例样式

目前实施例标题存在，但需要从“概念说明”升级为“可执行表格”。建议每个实施例至少有以下表格：

| 字段 | 示例 |
| --- | --- |
| seed | 找附近的店，但不要便利店 |
| 语义不变量 | 目标为找店；排除便利店；位置约束为附近 |
| 可变自由度 | 实体自由度：店类型；表达自由度：口语/追问；场景自由度：车载导航 |
| 互斥约束 | 店类型候选不得为便利店 |
| 原始预算 | 实体 20，表达 10，场景 5 |
| 投影后预算 | 实体 14，表达 8，场景 5 |
| 生成样本 | 找附近有停车场的餐厅，不要便利店 |
| 裂变轨迹 | seed_001 -> entity:餐厅 -> expression:口语 -> guard:pass |
| 失败反馈 | 某批实体候选命中便利店，归因到实体自由度候选来源 |
| 下一轮变化 | 降低该候选来源预算，提高实体过滤规则权重 |

这个表格比单纯写公式更能证明“本领域技术人员能够实现”。

## 5. 两案优先级和返工策略

### 5.1 优先级

| 优先级 | 案件 | 原因 |
| --- | --- | --- |
| P0 | 失败证据数据资产生成方法及系统 | 与代码、产品、评测模式最贴近，已有代理人一页纸、权利要求骨架和事实锁定表，最容易返工通过。 |
| P1 | 语义自由度预算的语料裂变控制方法及系统 | 技术叙事完整，但需要补真实实施例和降低概念密度，建议作为第二波。 |

### 5.2 不建议做的事

1. 不建议用 BypassAIGC 或同类 humanizer 直接处理正文。
2. 不建议把检测分作为唯一验收标准。
3. 不建议为降低 AI 味删掉关键数据结构和技术细节。
4. 不建议把“未实现项”硬写成已经实现。
5. 不建议把第二案的实体池、在线检索、模板填槽写成核心，否则会退化成普通语料扩写。

### 5.3 建议做的事

1. 为每件案子生成“发明人事实确认表”。
2. 把技术问题压缩成一个主问题和少量从属问题。
3. 给每个独权特征找说明书支撑位置。
4. 给每个说明书实施例标注来源：代码、文档、测试数据、发明人口述、推演。
5. 将 AI 参与限制在语言检查、完整性检查、一致性检查、法条风险提示，不让 AI 直接创造技术方案。

## 6. 发明人事实确认表模板

返工前，每个关键特征建议按以下方式锁定。

| 技术特征 | 当前写法 | 事实状态 | 证据来源 | 是否进独权 | 处理建议 |
| --- | --- | --- | --- | --- | --- |
| 字段角色识别 | 基于字段名、内容和别名表映射角色 | 已实现/需确认 | `algorithm/src/app.py`、`src/utils/evaluationMode.ts` | 是 | 用上位表述，不绑定具体别名表 |
| 期望行为补全 | 从备注、工具 schema、上下文补期望 | 部分实现/需确认 | 代码和发明人口述 | 谨慎 | 独权写候选期望行为，来源/置信度放从权 |
| 失败信号提取 | 根据 expected/actual 差异提取 | 已实现 | `EVAL_SIGNAL_CONFIG` 等 | 是 | 独权写失败信号，不列全枚举 |

## 7. 红队执行清单

每件案子返工前先打以下清单。

### 7.1 充分公开检查

- [ ] 是否写清输入数据的来源和字段形态。
- [ ] 是否写清核心中间对象的数据结构。
- [ ] 是否写清每一步处理规则或可替代实现。
- [ ] 是否写清低置信度、缺字段、质量不达标时的处理路径。
- [ ] 是否至少有 2 个可实施例支撑核心上位概括。
- [ ] 是否有一个完整样本从输入到输出走完全链路。

### 7.2 权利要求支持检查

- [ ] 独权中每个名词都能在说明书找到定义或实施例。
- [ ] 独权中每个动作都能在流程中找到对应步骤。
- [ ] 独权中的上位概括没有超出实施例支撑范围。
- [ ] 从权细节没有反向变成独权必需特征。

### 7.3 单一性检查

- [ ] 一件案子只围绕一个总发明构思。
- [ ] 所有从属特征都围绕同一个主链服务。
- [ ] 与主链弱相关的功能只作为可选实施方式，不作为第二核心。

### 7.4 超范围风险检查

- [ ] 所有后续可能想保护的关键字段已经在首稿出现。
- [ ] 所有后续可能想保护的关键分支已经在首稿出现。
- [ ] 所有后续可能想保护的关键图示关系已经在首稿出现。
- [ ] 未实现或未确认内容没有被写成既成事实。

### 7.5 AI 使用合规检查

- [ ] 技术问题由发明人或项目事实确定。
- [ ] 技术方案由项目事实、代码、设计文档或发明人口述支撑。
- [ ] AI 只做语言、结构、一致性和风险检查。
- [ ] 保留事实锁定表和修订记录，能说明每个技术特征来源。

## 8. 蓝队返工路线

### 阶段一：主案事实锁定

目标：让主案从“文档看起来完整”变成“每个关键技术特征都有来源”。

动作：

1. 用代码和 docs 填写第 6 节事实确认表。
2. 把未实现项分为：删除、降级为可选实施方式、补代码、发明人口述确认。
3. 输出主案“代理人一页纸 v2”。

验收：

- 独权不依赖未实现字段。
- 说明书仍保留足够宽的可选实施方式。
- 代理人能直接据此写权利要求。

### 阶段二：主案样章返工

先不改全文，只改：

1. B1 技术问题。
2. B2.1 方法流程。
3. 实施例二或实施例四。
4. 附图说明。

验收标准：

- 技术问题只保留一个主问题。
- 方法流程形成闭环。
- 实施例能从输入样本走到输出资产。
- 不出现“为了显著提升”等空泛效果句。

### 阶段三：第二案实施例补强

目标：降低概念堆叠感，补足可实施性。

动作：

1. 为 3 个 seed 补完整账本表。
2. 为 1 个失败反馈补完整预算回写表。
3. 将 B1 的 9 个具体问题压缩为 1 个主问题 + 4 个从属问题。
4. 将 B4 的 10 步主线压缩为 6-8 个独权步骤。

验收：

- 读者能手工模拟一次裂变预算投影和反馈回写。
- 不需要理解全部公式也能实施基础方案。

### 阶段四：文本风险复核

最后才处理 AI 检测风险。

原则：

1. 检测分只定位高风险段落，不指导改写方向。
2. 高风险段落先检查是否缺事实、缺分支、缺实施例。
3. 若段落已经技术上必要，不为检测器牺牲法律表达。
4. 不使用“绕过检测”的工具链处理正式文本。
